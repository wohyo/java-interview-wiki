# 13. 线程池

**一句话定位**：`ThreadPoolExecutor` 用**核心线程 + 阻塞队列 + 非核心线程 + 拒绝策略**四级缓冲管理任务，理解它的关键是搞清“任务什么时候进队列、什么时候加线程”。

## 一、七个参数

```java
public ThreadPoolExecutor(int corePoolSize,        // 核心线程数（常驻，默认不超时回收）
                          int maximumPoolSize,     // 最大线程数
                          long keepAliveTime,      // 非核心线程空闲存活时间
                          TimeUnit unit,
                          BlockingQueue<Runnable> workQueue,  // 工作队列
                          ThreadFactory threadFactory,        // 线程工厂（命名、异常处理）
                          RejectedExecutionHandler handler)   // 拒绝策略
```

## 二、任务提交的执行流程

```text
submit(task)
   │
   ├─ ① 当前线程数 < corePoolSize → 新建核心线程执行
   │
   ├─ ② 核心线程已满 → 尝试放入 workQueue
   │        ├─ 入队成功 → 等待空闲线程取走
   │        └─ 入队失败（队列满）→ ③
   │
   ├─ ③ 当前线程数 < maximumPoolSize → 新建非核心线程执行
   │
   └─ ④ 已达最大线程数 → 执行拒绝策略
```

源码里对应 `execute()`：

```java
public void execute(Runnable command) {
    if (command == null) throw new NullPointerException();
    int c = ctl.get();
    if (workerCountOf(c) < corePoolSize) {          // ①
        if (addWorker(command, true)) return;
        c = ctl.get();
    }
    if (isRunning(c) && workQueue.offer(command)) { // ②
        int recheck = ctl.get();
        if (!isRunning(recheck) && remove(command))
            reject(command);
        else if (workerCountOf(recheck) == 0)
            addWorker(null, false);
    }
    else if (!addWorker(command, false))            // ③
        reject(command);                            // ④
}
```

### 为什么先入队、后扩线程

这是面试高频追问。设计意图是**尽量复用已有线程**：创建线程有成本（栈内存、内核对象），队列能缓冲就先缓冲。代价是：

- 如果用**无界队列**（`LinkedBlockingQueue` 默认容量 `Integer.MAX_VALUE`），队列永远不会满，`maximumPoolSize` 形同虚设，线程数永远停在 `corePoolSize`；
- 任务堆积过多会导致内存上涨，甚至 OOM。

`Executors.newFixedThreadPool()` 就是这种组合，所以《阿里巴巴 Java 开发手册》禁止用 `Executors` 创建线程池，要求手动 `new ThreadPoolExecutor` 并指定有界队列。

## 三、四种拒绝策略

| 策略 | 行为 | 适用 |
| --- | --- | --- |
| `AbortPolicy`（默认） | 抛 `RejectedExecutionException` | 需要感知失败、快速失败 |
| `CallerRunsPolicy` | 调用者线程自己执行 | 反压：让提交任务的一方慢下来 |
| `DiscardPolicy` | 静默丢弃，不报错 | 允许丢任务的场景（极少用） |
| `DiscardOldestPolicy` | 丢弃队列中最老的任务，再提交当前任务 | 只关心最新数据（如实时位置） |

自定义策略可以实现 `RejectedExecutionHandler`，比如落库、写 MQ 稍后重试。

## 四、线程池状态

`ctl` 是一个 `AtomicInteger`，高 3 位存状态，低 29 位存线程数：

| 状态 | 含义 |
| --- | --- |
| `RUNNING` | 接受新任务，处理队列任务 |
| `SHUTDOWN` | 不接受新任务，继续处理队列任务（`shutdown()`） |
| `STOP` | 不接受新任务，不处理队列，中断正在执行的任务（`shutdownNow()`） |
| `TIDYING` | 所有任务结束，线程数为 0，准备执行 `terminated()` |
| `TERMINATED` | `terminated()` 执行完毕 |

状态只能按 `RUNNING → SHUTDOWN → STOP → TIDYING → TERMINATED` 单向流转。

## 五、线程数怎么设

| 类型 | 经验公式 | 说明 |
| --- | --- | --- |
| CPU 密集型 | `N + 1` | N 为核数，+1 是为了在偶发缺页时补位 |
| IO 密集型 | `2N` ~ `N / (1 - 阻塞系数)` | 阻塞系数 0.8~0.9 时约为 5N~10N |
| 混合型 | 拆成两个池 | 避免 IO 阻塞拖累 CPU 任务 |

但公式只是起点，最终要**压测**：看 QPS、P99 延迟、CPU 利用率、队列长度。线程太多会加剧上下文切换和内存占用，线程太少会排队。

一个更实用的口径（Little's Law）：

```
所需线程数 ≈ QPS × 平均处理时间（秒）
```

比如 QPS 1000、平均耗时 50ms，理论需要 50 个并发线程，再留 20%~30% 余量。

## 六、execute 与 submit

| 维度 | `execute(Runnable)` | `submit(Callable/Runnable)` |
| --- | --- | --- |
| 返回值 | 无 | `Future` |
| 异常处理 | 抛到线程的 `UncaughtExceptionHandler` | 捕获并存入 `Future`，`get()` 时抛 `ExecutionException` |
| 适用 | 不关心结果 | 需要结果/取消/超时 |

`submit` 的坑：**异常被吞进 Future**，如果从不调用 `get()`，任务失败了也无人知晓。要么 `get()` 检查，要么在任务内部自己 try-catch 记日志。

## 七、必须知道的坑

### 1. 无界队列 + 固定线程数

```java
// 危险：队列无界，max 永远用不上
new ThreadPoolExecutor(4, 4, 0, TimeUnit.SECONDS, new LinkedBlockingQueue<>());

// 推荐：有界队列 + 明确的拒绝策略
new ThreadPoolExecutor(
    8, 16, 60, TimeUnit.SECONDS,
    new ArrayBlockingQueue<>(1000),
    new ThreadFactory() {
        private final AtomicInteger seq = new AtomicInteger();
        public Thread newThread(Runnable r) {
            Thread t = new Thread(r, "order-pool-" + seq.incrementAndGet());
            t.setUncaughtExceptionHandler((th, e) -> log.error("task failed", e));
            return t;
        }
    },
    new ThreadPoolExecutor.CallerRunsPolicy());
```

### 2. 线程池隔离

不要所有业务共用一个线程池：一个慢接口（比如调用第三方超时）会把线程占满，拖垮其他业务。按业务拆分，各自配置队列和拒绝策略。

### 3. 优雅关闭

```java
executor.shutdown();                                  // 不再接受新任务
if (!executor.awaitTermination(30, TimeUnit.SECONDS)) {
    executor.shutdownNow();                           // 中断剩余任务
}
```

`shutdownNow()` 只是给线程发中断信号，任务是否响应中断取决于代码里有没有检查 `Thread.interrupted()`。

### 4. 线程泄漏

任务里 `catch (Throwable)` 后不抛出、或者死循环不响应中断，都会让线程无法回收。用 `ThreadFactory` 统一命名，便于 `jstack` 排查。

## 八、监控

| 指标 | 获取方式 |
| --- | --- |
| 活跃线程数 | `getActiveCount()` |
| 池大小 | `getPoolSize()` |
| 队列长度 | `getQueue().size()` |
| 已完成任务数 | `getCompletedTaskCount()` |
| 拒绝次数 | 自定义 `RejectedExecutionHandler` 计数 |

队列长度持续增长、活跃线程数长期等于最大值，说明池子不够或下游变慢，需要扩容或限流。

## 九、面试连环问

**Q：线程池的核心参数和执行流程？**

七个参数：核心线程数、最大线程数、空闲时间、时间单位、工作队列、线程工厂、拒绝策略。流程：核心线程 → 队列 → 非核心线程 → 拒绝。

**Q：为什么先放队列再扩线程？**

为了复用线程、减少创建开销。代价是无界队列会让 `maximumPoolSize` 失效，所以必须用有界队列。

**Q：`shutdown()` 和 `shutdownNow()` 的区别？**

`shutdown()` 是 `SHUTDOWN` 状态：不再接新任务，队列里的任务继续执行完；`shutdownNow()` 是 `STOP` 状态：不接新任务、丢弃队列、中断正在执行的任务，返回未执行的任务列表。

**Q：线程数怎么定？**

CPU 密集型 `N+1`，IO 密集型 `2N` 或 `N/(1-阻塞系数)`，实际用 `QPS × 耗时` 估算后压测调整。

**Q：`execute` 和 `submit` 的区别？**

`submit` 返回 `Future`，异常被封装进 Future，`get()` 时才抛出；`execute` 没有返回值，异常直接抛给线程的异常处理器。用 `submit` 一定要处理 `get()` 的异常。

**Q：为什么禁用 `Executors`？**

`newFixedThreadPool` / `newSingleThreadExecutor` 用无界队列，可能 OOM；`newCachedThreadPool` 最大线程数是 `Integer.MAX_VALUE`，可能创建海量线程。手动创建可以明确队列容量和拒绝策略。

**Q：线程池里的线程抛异常会怎样？**

线程会结束，线程池会补一个新线程。异常由 `Thread.UncaughtExceptionHandler` 处理；如果是 `submit` 提交，异常被 `FutureTask` 捕获，不会触发 uncaught handler。
