# 18. JVM 调优

**一句话定位**：调优不是“背参数”，而是**先测量、后定位、再改一个变量**——大多数线上问题不是参数没调好，而是代码里有内存泄漏、大对象、线程数失控。

## 一、常用参数

### 堆与栈

```bash
-Xms4g -Xmx4g                 # 堆初始/最大，生产建议相等，避免动态扩容抖动
-Xss1m                       # 单线程栈大小，递归深/栈帧大时调大
-XX:NewRatio=2               # 老年代:新生代 = 2:1
-XX:SurvivorRatio=8          # Eden:Survivor = 8:1
-XX:PretenureSizeThreshold=1m # 大对象直接进老年代（只对 Serial/ParNew 有效）
```

### 元空间

```bash
-XX:MetaspaceSize=256m        # 首次触发 Metaspace GC 的水位（不是初始容量）
-XX:MaxMetaspaceSize=256m     # 上限，生产必须设，防止类加载泄漏吃光内存
```

注意 `MetaspaceSize` 的含义：它是**触发 GC 的阈值**，不是“初始分配 256m”。不设上限时默认只受本地内存限制。

### GC 选择

```bash
-XX:+UseG1GC                  # JDK 9+ 默认
-XX:MaxGCPauseMillis=200      # G1 的目标停顿（软目标）
-XX:G1HeapRegionSize=8m       # Region 大小，1~32MB 的 2 的幂
-XX:+UseZGC                   # 大堆、低延迟；JDK 21 可加 -XX:+ZGenerational
```

::: warning
一个常见误区：**用了 G1 还去设 `-Xmn`**。G1 靠动态调整新生代大小来满足停顿目标，固定 `-Xmn` 会限制它的弹性，通常不建议。

:::

### 故障排查

```bash
-XX:+HeapDumpOnOutOfMemoryError
-XX:HeapDumpPath=/data/dump/
-XX:ErrorFile=/data/hs_err_pid%p.log
-Xlog:gc*:file=/data/logs/gc.log:time,uptime,level,tags:filecount=10,filesize=50m
```

`-Xlog` 是 JDK 9+ 的统一日志框架；JDK 8 要写 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:...`。面试如果问“GC 日志参数”，先确认 JDK 版本。

## 二、CPU 100% 排查

Linux 上的标准流程：

```bash
# 1. 找到 CPU 最高的 Java 进程
top

# 2. 找到该进程内 CPU 最高的线程
top -Hp <pid>

# 3. 线程 ID 转十六进制（jstack 里是 nid=0x...）
printf '%x\n' <tid>

# 4. 抓线程栈，按 nid 定位
jstack <pid> > /tmp/stack.txt
grep -A 30 'nid=0x<hex>' /tmp/stack.txt
```

定位后按栈特征判断：

| 栈特征 | 可能原因 |
| --- | --- |
| 业务线程停在某个 `while`/递归 | 死循环、算法复杂度爆炸 |
| 大量线程 `BLOCKED` 在同一把锁 | 锁竞争、临界区过长 |
| `GC task thread` 占比高 | 频繁 GC，转去查内存 |
| `C2 CompilerThread` 高 | JIT 编译热点方法（通常短暂，持续高需注意） |
| `nioEventLoopGroup` 高 | 网络/序列化热点，用 async-profiler 看火焰图 |

更高效的工具：`async-profiler` 采样生成火焰图，能直接看到热点方法；`arthas` 的 `thread -n 3` 可以一步列出最忙的三个线程。

## 三、内存问题排查

### 频繁 Full GC

```bash
jstat -gcutil <pid> 1000        # 每秒打印一次各区使用率和 GC 次数
```

关注三列：`O`（老年代使用率）是否持续接近 100%、`FGC` 是否快速增长、`FGCT`（Full GC 总耗时）是否持续上升。

判断方向：

| 现象 | 结论 |
| --- | --- |
| 老年代缓慢上涨，Full GC 后降不下来 | 内存泄漏 |
| 老年代涨得快、每次 Full GC 能降回低位 | 晋升过快（新生代太小 / 大对象多 / 缓存太大） |
| Full GC 后元空间不降 | 类加载泄漏（动态代理、热部署） |

### 堆转储

```bash
jmap -dump:live,format=b,file=/tmp/heap.hprof <pid>
# 或
jcmd <pid> GC.heap_dump /tmp/heap.hprof
```

用 MAT / JProfiler 打开，先看 **Leak Suspects**，再看支配树（Dominator Tree）——按“保留大小”排序，最大的那棵通常就是元凶。

::: warning
`jmap -dump` 会 STW，线上大堆可能停顿数秒，优先用 `-XX:+HeapDumpOnOutOfMemoryError` 自动 dump，或用 `jcmd` 的低开销方式。

:::

### 堆外内存

堆看起来正常但进程 RSS 一直涨，查直接内存：

```bash
jcmd <pid> VM.native_memory summary     # 需启动时加 -XX:NativeMemoryTracking=summary
```

Netty 的 `ByteBuf` 泄漏可以用 `-Dio.netty.leakDetection.level=paranoid` 定位。

## 四、线程问题排查

```bash
jstack <pid> > /tmp/stack.txt
```

| 现象 | 命令/判断 |
| --- | --- |
| 死锁 | `jstack` 输出末尾会直接打印 `Found one Java-level deadlock` |
| 线程数暴涨 | `jstack <pid> \| grep 'java.lang.Thread.State' \| sort \| uniq -c` |
| 线程池打满 | 搜线程名（如 `pool-1-thread-`），看是否都停在 `take()`/`getTask()` |
| 长时间 WAITING | 看栈顶方法，常见是 `park`、`wait`、`sleep` |

## 五、调优的正确顺序

1. **量化目标**：吞吐优先还是延迟优先？P99 目标多少？内存预算多少？
2. **压测基线**：固定流量，记录 TP99、GC 次数、CPU、内存曲线。
3. **只改一个变量**：每次只调一个参数，重跑压测，对比数据。
4. **优先改代码**：对象创建量、缓存大小、线程池配置、SQL，往往比调 JVM 参数收益大。
5. **留出余量**：堆不要占满物理内存，给元空间、直接内存、线程栈、操作系统留空间。

一条实践经验：**G1/ZGC 时代，JVM 参数已经很少需要精调**。`-Xms=-Xmx`、设 `MaxMetaspaceSize`、开 GC 日志和 OOM dump，基本就够；剩下的问题大多在应用层。

## 六、面试连环问

**Q：JVM 调优调什么？**

调三件事：堆大小与分代比例、GC 收集器与停顿目标、故障排查相关的日志/dump 参数。调优的前提是明确目标（吞吐/延迟）和基线数据，而不是套模板。

**Q：CPU 100% 怎么排查？**

`top` 找进程 → `top -Hp` 找线程 → `printf '%x'` 转十六进制 → `jstack` 按 `nid` 定位栈 → 判断是死循环、锁竞争还是 GC。更快的做法是 async-profiler 火焰图。

**Q：频繁 Full GC 怎么排查？**

`jstat -gcutil` 看老年代曲线和 FGC 增速；如果 Full GC 后老年代降不下来，dump 堆用 MAT 找泄漏；如果降得下来但涨得快，查晋升过快（新生代太小、大对象、缓存无上限）。

**Q：`-Xms` 和 `-Xmx` 为什么要设成一样？**

避免堆在运行期反复扩容/缩容。扩容会触发 Full GC 和内存整理，缩容会让已提交内存还给操作系统再重新申请，都会带来抖动。

**Q：G1 的 `MaxGCPauseMillis` 设得越小越好吗？**

不是。它越小，G1 每次只敢回收少量 Region，回收速度跟不上分配速度，最终可能触发 Full GC，反而更慢。要根据实际延迟目标和堆大小设一个可达到的值（常见 100~300ms）。

**Q：线上应该开 `-XX:+DisableExplicitGC` 吗？**

::: warning
多数情况建议开，防止代码/框架里的 `System.gc()` 触发 Full GC。但要注意：NIO 的 `DirectByteBuffer` 依赖 `System.gc()` 触发 Cleaner 回收堆外内存，禁用后堆外内存可能回收不及时，需要配合 `-XX:MaxDirectMemorySize` 和显式释放。

:::

**Q：JDK 8 和 JDK 17 的 GC 日志参数有什么区别？**

JDK 8 用 `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:`；JDK 9+ 统一为 `-Xlog:gc*:file=...`，支持按 tag 过滤、按大小滚动。旧参数在新版本会被忽略或报错。
