# 25. Redis 过期策略

**一句话定位**：Redis 的过期 = **惰性删除 + 定期删除**；内存满时再叠加**淘汰策略**（LRU/LFU/random/ttl）。过期解决“该不该删”，淘汰解决“内存不够删谁”。

## 一、过期时间存在哪

Redis 有两个字典：

| 字典 | key | value |
| --- | --- | --- |
| `dict` | 所有 key | 值对象 |
| `expires` | 设置了过期时间的 key | 过期时间戳（毫秒） |

```bash
EXPIRE key 60          # 60 秒后过期
PEXPIRE key 60000      # 毫秒
TTL key                # 剩余秒数，-1 表示没有过期时间，-2 表示 key 不存在
PERSIST key            # 移除过期时间，变成永不过期
SET key value EX 60    # 原子地设值 + 设过期
```

`SET key value EX 60` 和 `SET key value` + `EXPIRE key 60` 的区别：前者原子；后者两条命令之间若中断（比如第二条执行失败），key 会永不过期。

## 二、惰性删除

访问 key 时才检查是否过期：

```c
// 伪代码
robj *lookupKeyRead(redisDb *db, robj *key) {
    expireIfNeeded(db, key);        // 过期就删（并传播 DEL 给从库/AOF）
    return dictFetchValue(db->dict, key);
}
```

- 优点：CPU 友好，不访问就不检查；
- 缺点：**永不访问的 key 永远不会被删**，内存只增不减。

所以需要定期删除兜底。

## 三、定期删除

Redis 默认每秒执行 10 次（`hz = 10`，即每 100ms 一次）后台任务 `activeExpireCycle`：

```text
每个 DB 重复：
  ① 随机抽取 20 个设置了过期时间的 key
  ② 删除其中已过期的
  ③ 如果这 20 个里过期比例 > 25%，回到 ① 继续抽
  ④ 达到时间上限（默认不超过 25% CPU 时间）就退出
```

三个细节：

1. **随机抽样，不是全量扫描**。全量扫描会阻塞主线程。
2. **25% 阈值**：过期比例高说明这个 DB 里积压了很多过期 key，继续抽；低于阈值说明清理得差不多了，换下一个 DB。
3. **有时间上限**：避免一轮定期删除占用过多 CPU，影响正常请求。

这套算法是“抽样 + 自适应”，保证过期 key 最终会被清理，但**不保证及时**——极端情况下（大量 key 同时过期、且抽样一直没抽到），会有延迟。

## 四、主从复制下的过期

**从库不主动过期**，只等主库同步 `DEL`：

```
主库：key 过期 → 删除 → 向从库传播 DEL
从库：收到 DEL 才删
```

原因：过期是写操作，必须由主库统一决策，否则主从数据不一致。

但这带来一个问题：从库上已经逻辑过期的 key 还占着内存。Redis 3.2+ 做了处理：**从库读请求遇到逻辑过期的 key 会返回空**（数据暂时保留，等主库的 DEL），既保证读一致性，又不会立即破坏主从数据。

如果主库长期不删除（比如主库负载高、定期删除没轮到），从库内存会偏高，这是正常现象，不是 bug。

## 五、RDB / AOF 对过期 key 的处理

| 场景 | 行为 |
| --- | --- |
| RDB 生成 | 已过期的 key 不会被写入 |
| RDB 加载（主库） | 过期的 key 不会被加载 |
| RDB 加载（从库） | 全部加载（因为从库不主动过期，等主库 DEL） |
| AOF 写入 | 过期删除会追加一条 `DEL` |
| AOF 重写 | 已过期的 key 会被过滤，不写入新 AOF |

所以在从库上 `DBSIZE` 可能比主库大，属于预期行为。

## 六、内存淘汰策略

当 `used_memory > maxmemory` 时，按 `maxmemory-policy` 淘汰：

| 策略 | 范围 | 算法 | 说明 |
| --- | --- | --- | --- |
| `noeviction` | — | 不淘汰 | **默认**，写命令直接报错 `OOM command not allowed` |
| `allkeys-lru` | 所有 key | 近似 LRU | 最常用，缓存场景首选 |
| `allkeys-lfu` | 所有 key | 近似 LFU | Redis 4.0+，按访问频率淘汰 |
| `allkeys-random` | 所有 key | 随机 | 随机淘汰，命中率不稳定 |
| `volatile-lru` | 有 TTL 的 key | 近似 LRU | 只淘汰设置了过期时间的 |
| `volatile-lfu` | 有 TTL 的 key | 近似 LFU | Redis 4.0+ |
| `volatile-random` | 有 TTL 的 key | 随机 | |
| `volatile-ttl` | 有 TTL 的 key | 剩余 TTL 最小优先 | 优先淘汰快过期的 |

选择建议：

- **纯缓存**：`allkeys-lru`，所有 key 都可以淘汰；
- **缓存 + 持久数据混存**：`volatile-lru`，只淘汰缓存 key，持久数据不受影响；
- **热点集中、有明确高频访问**：`allkeys-lfu`，比 LRU 更适合“访问频率差异大”的场景；
- **不能丢数据**：`noeviction` + 监控告警，内存满了宁可报错也不淘汰。

### 为什么是“近似 LRU”

真正的 LRU 需要维护双向链表，每次访问都移动节点，内存和 CPU 成本都高。Redis 用**采样**：

```text
淘汰时：
  ① 随机取 maxmemory-samples（默认 5）个 key
  ② 比较它们的 lru 时间戳（24 bit 时钟）
  ③ 淘汰最久未使用的那个
```

采样 5 个的效果已经接近真实 LRU；调大 `maxmemory-samples` 更精确但更慢。Redis 3.0 后还有一个**淘汰池**（16 个候选），把多次采样的结果累积起来，进一步提高精度。

### LRU 和 LFU 的区别

| 维度 | LRU | LFU |
| --- | --- | --- |
| 依据 | 最后一次访问时间 | 访问频率（带衰减） |
| 弱点 | 偶发一次全表扫描会污染缓存 | 新 key 难以积累频率，需要预热 |
| Redis 实现 | 24 bit 时钟 | 8 bit 计数 + 8 bit 衰减时间 |
| 适用 | 访问有局部性 | 热点稳定、频率差异大 |

LFU 的计数器不是简单 +1：访问一次加一个概率性增量（`lfu-log-factor` 控制增长难度），并且随时间衰减（`lfu-decay-time`），避免老热点永远占着位置。

## 七、过期与淘汰的关系

```
key 到期 —— 该不该删？ —— 惰性删除 + 定期删除
内存满了 —— 删谁？    —— maxmemory-policy 淘汰
```

两者独立：过期策略管“逻辑上已失效”，淘汰策略管“物理内存不够”。一个 key 可能还没到期就被淘汰，也可能到期了但因为没被访问、抽样没抽到而暂时还占着内存。

## 八、面试连环问

**Q：Redis 的过期策略有哪些？**

惰性删除（访问时检查）+ 定期删除（每 100ms 随机抽 20 个，过期比例超过 25% 就继续抽，有时间上限）。两者配合，兼顾 CPU 和内存。

**Q：为什么不用定时器给每个 key 精确删除？**

key 数量可能上亿，每个 key 一个定时器，内存和 CPU 都扛不住。抽样是工程上的折中。

**Q：过期 key 会立刻释放内存吗？**

惰性删除和定期删除都会调用 `del`，但 `del` 只是把 key 从字典移除，内存由分配器管理，不一定立刻还给操作系统。大 key 删除还可能造成阻塞，Redis 4.0+ 提供 `UNLINK` 异步删除。

**Q：从库的 key 过期了会自己删吗？**

不会。从库等主库同步 `DEL`，自己不做过期删除（保证主从一致）。Redis 3.2+ 从库读已逻辑过期的 key 会返回空。

**Q：`noeviction` 是默认策略，为什么线上不建议用？**

内存满了之后所有写命令都报错，读还能用，但业务基本已经不可用。缓存场景应该显式设置 `allkeys-lru` 或 `volatile-lru`。

**Q：LRU 和 LFU 怎么选？**

访问模式有局部性（最近访问的还会访问）用 LRU；热点稳定、频率差异大（少量 key 被反复访问）用 LFU。LFU 对突发的新热点不友好，需要预热。

**Q：`maxmemory` 应该设多大？**

小于物理内存，给 RDB fork 的写时复制、AOF 重写、客户端缓冲区留余量。经验值是物理内存的 60%~75%，具体看持久化配置和业务写入量。
