# 10. synchronized 原理

**一句话定位**：`synchronized` 编译后是 `monitorenter/monitorexit`，运行期对应对象头里的 **Monitor（管程）**；JVM 为了减少内核态切换，让它从偏向锁一路升级到重量级锁。

## 一、三种写法与字节码

```java
// ① 同步代码块：锁是括号里的对象
synchronized (lock) {
    count++;
}

// ② 同步实例方法：锁是 this
public synchronized void inc() { count++; }

// ③ 同步静态方法：锁是 Class 对象
public static synchronized void inc() { count++; }
```

①②的字节码差别很大：

```text
// 同步代码块
monitorenter
  ... 业务字节码 ...
monitorexit          ← 正常出口
  goto end
  monitorexit        ← 异常出口（编译器自动加的，保证异常也能释放）
end:

// 同步方法：没有 monitorenter，靠 ACC_SYNCHRONIZED 标志
public synchronized void inc();
  flags: ACC_PUBLIC, ACC_SYNCHRONIZED
```

同步方法不加 `monitorenter`，JVM 在方法调用时检查 `ACC_SYNCHRONIZED` 自动加锁、返回时自动释放。这就是“同步方法不会因为异常不释放锁”的原因——释放由 JVM 保证，不依赖字节码。

## 二、Monitor 的内部结构

每个 Java 对象都关联一个 Monitor（HotSpot 用 `ObjectMonitor` 实现）：

```
ObjectMonitor
├── _owner        当前持有锁的线程
├── _recursions   重入次数
├── _EntryList    阻塞等待锁的线程（BLOCKED）
├── _WaitSet      调用 wait() 后释放锁、等待唤醒的线程（WAITING）
└── _count        计数
```

线程进入 `synchronized` 的流程：

1. `monitorenter`：尝试把 `_owner` 设为自己；
2. 成功 → 执行，`_recursions++`（可重入）；
3. 失败 → 进入 `_EntryList` 阻塞，等待 `_owner` 释放后被唤醒重新竞争；
4. `monitorexit`：`_recursions--`，减到 0 时释放锁并唤醒 `_EntryList` 里的线程。

`wait()` 会把线程从 `_owner` 移到 `_WaitSet` 并**完全释放锁**；`notify()` 把它移回 `_EntryList`，**但不会立刻释放锁**，要等当前线程退出同步块。这也是 `wait` 必须写在 `synchronized` 里的原因——不持有 monitor 就没有资格操作等待队列。

## 三、对象头与 Mark Word

64 位 JVM 下对象头占 12 字节（压缩指针开启）：`Mark Word`（8 字节）+ `Klass Pointer`（4 字节）。

Mark Word 的布局随锁状态变化：

| 锁状态 | 62 bit 内容 | 分代年龄 | 偏向标志 | 锁标志位 |
| --- | --- | --- | --- | --- |
| 无锁 | unused + hashCode | 4 bit | 0 | 01 |
| 偏向锁 | 持有锁的线程 ID（54 bit）+ epoch（2 bit） | 4 bit | 1 | 01 |
| 轻量级锁 | 指向栈中 Lock Record 的指针 | 4 bit | — | 00 |
| 重量级锁 | 指向 ObjectMonitor 的指针 | 4 bit | — | 10 |
| GC 标记 | 转发指针 | — | — | 11 |

关键点：**锁状态记录在对象头里，不需要额外分配锁对象**。这也是 `synchronized` 比 `ReentrantLock` 省空间的原因。

::: warning
偏向锁和 `hashCode` 互斥。对象一旦调用过 `Object.hashCode()`（或 `System.identityHashCode`），Mark Word 里要存 hash，就没有位置存线程 ID，偏向锁会失效。这是“偏向锁撤销”的常见触发点之一。

:::

## 四、锁升级

```
无锁
 │  第一个线程进入
 ▼
偏向锁（CAS 把线程 ID 写进 Mark Word，之后同一线程只比较 ID）
 │  出现第二个线程竞争
 ▼
轻量级锁（CAS 把 Mark Word 指向线程栈中的 Lock Record，失败则自旋）
 │  自旋失败 / 自旋线程过多 / 调用 wait
 ▼
重量级锁（ObjectMonitor + 操作系统互斥量，线程挂起）
```

**偏向锁**：适合“始终只有一个线程访问”的场景。第一次加锁用 CAS 写入线程 ID，之后同一线程进入只做一次 ID 比较，连 CAS 都省了。

**轻量级锁**：竞争出现时，撤销偏向，每个线程在自己的栈帧里建 Lock Record，用 CAS 把对象头指向它。CAS 成功即拿到锁；失败说明有竞争，开始**自旋**。

**自旋**：不放弃 CPU，循环重试 CAS，赌锁很快释放，避免线程挂起/唤醒的内核态开销。JDK 6 之后是**自适应自旋**：上次自旋成功过就多转几圈，总失败就少转或不转，次数由 JVM 动态调整。

**重量级锁**：自旋仍拿不到，升级为重量级锁，线程进入 `_EntryList` 挂起，由操作系统调度。唤醒需要用户态/内核态切换，开销最大。

**版本变化（面试常考的坑）**：

- JDK 6 引入偏向锁和轻量级锁；
- JDK 15（JEP 374）**默认禁用并废弃偏向锁**，`-XX:+UseBiasedLocking` 仍可开启；
- JDK 18 移除了偏向锁实现，相关参数失效。

所以现在（JDK 17/21）问“锁升级”，实际路径是 **无锁 → 轻量级锁 → 重量级锁**，偏向锁只作为历史知识回答。老面试题里的 `-XX:-UseBiasedLocking` 调优建议已经过时。

## 五、锁能降级吗

HotSpot 不支持严格意义上的锁降级（重量级不会退回轻量级）。`synchronized` 的锁在退出后直接回到无锁。

容易混淆的是**偏向锁的批量重偏向/批量撤销**：JVM 在安全点（SafePoint）统计撤销次数，超过阈值（默认 20 次）就把整个类的偏向锁批量撤销，之后新对象直接进入轻量级锁流程。这发生在安全点，不是运行中的“降级”。

## 六、锁消除与锁粗化

::: tip
JIT 的两个优化，面试常用来解释“synchronized 没你想的那么慢”：

| 优化 | 含义 | 例子 |
| --- | --- | --- |
| 锁消除 | 逃逸分析发现锁对象不会逃逸出方法，直接删掉同步 | 方法内 `new Object()` 当锁，外部拿不到，同步没意义 |
| 锁粗化 | 相邻的多次加锁合并成一次大锁 | 循环体内反复 `synchronized`，JIT 把锁提到循环外 |

:::

```java
// 锁消除的典型场景：StringBuffer 是局部变量
public String concat(String a, String b) {
    StringBuffer sb = new StringBuffer();   // 不会逃逸
    sb.append(a).append(b);                 // append 是 synchronized，但锁被消除
    return sb.toString();
}
```

## 七、synchronized 与 ReentrantLock

| 维度 | synchronized | ReentrantLock |
| --- | --- | --- |
| 实现层 | JVM（monitor） | JDK（AQS + CAS） |
| 释放 | 自动，异常也释放 | 必须 finally 中 `unlock()` |
| 可中断 | 不支持 | `lockInterruptibly()` |
| 超时 | 不支持 | `tryLock(timeout)` |
| 公平锁 | 不支持 | 支持（构造参数 true） |
| 条件变量 | 一个（wait/notify） | 多个 `Condition` |
| 可重入 | 支持 | 支持 |
| 性能 | JDK 6 后与 ReentrantLock 接近 | 高竞争下略优 |

选择原则：**能用 `synchronized` 就用**，需要超时、可中断、公平、多条件队列时才用 `ReentrantLock`。

## 八、面试连环问

**Q：synchronized 的锁是什么？**

对象锁。同步实例方法锁 `this`，同步静态方法锁 `Class` 对象，同步代码块锁括号里的对象。锁信息存在对象头的 Mark Word 里，不是额外的锁对象。

**Q：synchronized 怎么保证可见性？**

`monitorexit` 会把工作内存的修改刷回主内存（release 语义），`monitorenter` 会从主内存重新读取（acquire 语义）。JMM 层面就是“解锁 happens-before 后续对同一把锁的加锁”。内存屏障的细节见 [JMM](/guide/ext-jmm)。

**Q：锁升级的过程？JDK 17 还有偏向锁吗？**

无锁 → 偏向锁 → 轻量级锁 → 重量级锁。JDK 15 起偏向锁默认禁用，JDK 18 移除，所以 JDK 17 上默认是 无锁 → 轻量级 → 重量级，但可以用 `-XX:+UseBiasedLocking` 打开（17 还保留参数）。

**Q：为什么重量级锁慢？**

挂起和唤醒线程需要从用户态切换到内核态，由操作系统调度；轻量级锁的自旋在用户态完成，锁持有时间短时自旋更划算。

**Q：synchronized 是可重入的吗？怎么实现的？**

是。`ObjectMonitor._recursions` 记录重入次数，同一线程再次进入时计数 +1，退出时 -1，减到 0 才真正释放。可重入避免了“自己等自己”的死锁。

**Q：同步方法和同步代码块有什么区别？**

字节码层面：同步方法用 `ACC_SYNCHRONIZED` 标志，同步代码块用 `monitorenter/monitorexit`。语义一致，但同步代码块的锁范围更小、更灵活（可以锁任意对象），性能通常更好。

**Q：`wait()` 和 `sleep()` 的区别？**

`wait` 是 `Object` 方法，释放锁、进入 `_WaitSet`，只能被 `notify/notifyAll` 或超时唤醒，必须在 `synchronized` 内调用；`sleep` 是 `Thread` 静态方法，不释放锁，到点自动醒，任意位置可调用。
