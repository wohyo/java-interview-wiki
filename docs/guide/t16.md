# 16. 垃圾回收

**Q：如何判断对象可回收？**

引用计数法：每个对象维护引用计数器（循环引用无法回收，JVM 未使用）

可达性分析（JVM 采用）：从 GC Roots 向下搜索，不可达的对象可回收

GC Roots 包括：

栈帧中的局部变量引用的对象

静态变量引用的对象

JNI 引用（全局 JNI 引用）

活跃线程（Thread）

**Q：堆的分代结构？**

```
新生代 (Young Gen)    占堆 1/3
├── Eden    占新生代 8/10
└── S0, S1  各占 1/10（From 和 To，总 2/10）
老年代 (Old Gen)      占堆 2/3
```

对象优先在 Eden 分配

Minor GC 后 Eden 存活对象 → Survivor，年龄 +1

年龄 ≥ 15（默认，可通过 `-XX:MaxTenuringThreshold` 调）→ 进入老年代

**Q：三种 GC 算法的对比？**

| 算法 | 描述 | 优点 | 缺点 | 适用 |
| --- | --- | --- | --- | --- |
| 标记-清除 | 标记存活→清除死亡 | 快，不移动对象 | 产生碎片 | CMS 老年代 |
| 标记-复制 | Eden→Survivor | 无碎片 | 浪费 1 个 Survivor 空间 | 新生代 |
| 标记-整理 | 标记存活→向一端移动 | 无碎片，无空间浪费 | 需移动对象，STW 时间长 | 老年代 |

**🔥 Q：CMS 收集器的详细流程？**

```
1. 初始标记 (STW 短暂)       → 标记 GC Roots 直接可达的对象
2. 并发标记 (与用户线程并发)  → 从 GC Roots 遍历整个堆
3. 重新标记 (STW 较短暂)     → 修正并发标记期间变动的对象
4. 并发清除 (与用户线程并发)  → 清除死亡对象
```

优点：并发，低停顿

缺点：

产生碎片（标记-清除算法）

浮动垃圾：并发清除时产生的垃圾只能下次清理

CPU 敏感：并发阶段占用 CPU 资源

Concurrent Mode Failure：预留空间不够时退化为 Serial Old（STW 极长）

参数：`-XX:CMSInitiatingOccupancyFraction=70`

**🔥 Q：G1 收集器的原理？**

Region 化：堆分为 2048 个 Region（1~32MB），每个 Region 可以是Eden/Survivor/Old/Humongous

可预测停顿：`-XX:MaxGCPauseMillis=200` ，G1 通过选取最值得回收的 Region（回收收益最大）来满足停顿目标

过程：

`初始标记`` → ``并发标记`` → ``最终标记`` → ``筛选回收（``STW ``但只回收部分`` Region``）`

相比 CMS 的优势：

无碎片（标记-整理）

可预测停顿时间

自动管理大对象（Humongous Region）
