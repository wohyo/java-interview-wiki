# 16. 垃圾回收

**一句话定位**：GC 要解决三件事——**哪些对象还活着**（可达性分析）、**怎么回收**（标记清除/复制/标记整理）、**什么时候回收**（分代 + 收集器）。

## 一、怎么判断对象已死

### 引用计数（Java 没用）

每个对象维护一个计数器，被引用 +1、引用失效 -1，归零即回收。致命缺陷是**循环引用**：

```java
A.next = B;
B.next = A;
A = null; B = null;      // 两个对象互相引用，计数都不为 0，永远回收不掉
```

### 可达性分析（Java 在用）

从一组 **GC Roots** 出发做图遍历，走不到的对象即可回收。

GC Roots 包括：

| 类型 | 例子 |
| --- | --- |
| 虚拟机栈中引用的对象 | 方法参数、局部变量 |
| 方法区中静态属性引用的对象 | `static Object ref` |
| 方法区中常量引用的对象 | `static final` 引用 |
| 本地方法栈中 JNI 引用的对象 | native 方法持有的引用 |
| 活跃线程 | `Thread` 对象 |
| 同步锁持有的对象 | `synchronized(obj)` 中的 obj |
| JVM 内部引用 | 系统类加载器、基本类型的 Class 对象等 |

注意：**可达性分析不等于“立刻回收”**。真正回收前还有一次 `finalize()` 的机会（JDK 18 起默认关闭），对象可能“复活”，所以至少要经过两次标记。

## 二、四种引用

| 引用 | 回收时机 | 典型用途 |
| --- | --- | --- |
| 强引用 | 永不回收（除非不可达） | `new Object()` |
| 软引用 `SoftReference` | 内存不足时回收 | 内存敏感的缓存 |
| 弱引用 `WeakReference` | 下次 GC 就回收 | `ThreadLocalMap` 的 key、`WeakHashMap` |
| 虚引用 `PhantomReference` | 随时可能回收，只能配合 `ReferenceQueue` 感知 | 管理堆外内存（`DirectByteBuffer` 的 Cleaner） |

一个高频追问：`ThreadLocal` 的 key 是弱引用、value 是强引用，所以 key 被回收后 value 还在，线程池里线程长期存活就会泄漏——必须 `remove()`。

## 三、分代回收

分代建立在两个假说上：

1. **弱分代假说**：绝大多数对象朝生夕灭；
2. **强分代假说**：熬过越多次 GC 的对象越难死。

于是堆被切成新生代和老年代，用不同算法：

```
┌──────────── 新生代（1/3）────────────┬──── 老年代（2/3）────┐
│  Eden  │ Survivor0 │ Survivor1      │                     │
│  8     │ 1         │ 1              │                     │
└────────┴───────────┴────────────────┴─────────────────────┘
```

### 对象分配与晋升

1. 新对象优先在 **Eden** 分配（大对象直接进老年代，阈值 `-XX:PretenureSizeThreshold`，只对 Serial/ParNew 有效）；
2. Eden 满触发 **Minor GC**，存活对象复制到空的 Survivor，年龄 +1；
3. 两个 Survivor 轮换使用，始终有一个是空的；
4. 年龄达到 `-XX:MaxTenuringThreshold`（默认 15，因为对象头年龄只有 4 bit）晋升老年代；
5. **动态年龄判定**：Survivor 中同龄对象总和超过 Survivor 空间一半，年龄 ≥ 该值的对象直接晋升，不必等 15；
6. 老年代空间不足触发 **Major/Full GC**。

还有 **TLAB**（Thread Local Allocation Buffer）：每个线程在 Eden 里预先划一小块，分配对象不用 CAS 抢指针，减少竞争。

## 四、三种回收算法

| 算法 | 做法 | 优点 | 缺点 | 用在哪 |
| --- | --- | --- | --- | --- |
| 标记-清除 | 标记存活，清除未标记 | 实现简单、不移动对象 | 产生碎片、效率不稳 | CMS |
| 复制 | 存活对象复制到另一半 | 无碎片、分配快（指针碰撞） | 浪费一半空间 | 新生代 |
| 标记-整理 | 标记后把存活对象向一端移动 | 无碎片、不浪费空间 | 移动对象成本高、需 STW | 老年代 |

新生代对象存活率低，复制算法最划算；老年代存活率高，复制会浪费大量空间，所以用标记-整理。

## 五、收集器一览

| 收集器 | 作用区域 | 算法 | 停顿 | 备注 |
| --- | --- | --- | --- | --- |
| Serial | 新生代 | 复制 | STW | 单线程，Client 模式默认 |
| ParNew | 新生代 | 复制 | STW | Serial 的多线程版，常与 CMS 搭配 |
| Parallel Scavenge | 新生代 | 复制 | STW | 关注吞吐量，JDK 8 服务端默认 |
| Serial Old | 老年代 | 标记-整理 | STW | Serial 的老年代版 |
| Parallel Old | 老年代 | 标记-整理 | STW | 与 Parallel Scavenge 搭配 |
| CMS | 老年代 | 标记-清除 | 低停顿 | JDK 9 废弃，**JDK 14 移除** |
| G1 | 整堆 | 复制 + 标记整理 | 可预测 | JDK 9+ 默认 |
| ZGC | 整堆 | 并发标记/转移 | 亚毫秒 | JDK 11 实验，JDK 15 转正 |
| Shenandoah | 整堆 | 并发标记/转移 | 低 | OpenJDK 提供，非 Oracle JDK |

### CMS 的四个阶段

```
① 初始标记（STW，极短）  只标记 GC Roots 直接关联的对象
② 并发标记                从直接关联对象出发遍历整个对象图，与用户线程并发
③ 重新标记（STW，短）     修正并发标记期间因用户线程继续运行导致的变动（增量更新）
④ 并发清除                与用户线程并发清理
```

缺点：**浮动垃圾**（并发清除期间新产生的垃圾只能下次回收）、**并发模式失败**（预留空间不够，退化成 Serial Old 的 Full GC，停顿极长）、**内存碎片**（标记-清除不整理）。

### G1

G1 把堆切成大小相等的 **Region**（1~32MB，最多约 2048 个），每个 Region 动态扮演 Eden/Survivor/Old/Humongous：

```
┌────┬────┬────┬────┬────┬────┐
│ E  │ S  │ O  │ E  │ H  │ 空闲│      H = Humongous（大对象，跨多个 Region）
└────┴────┴────┴────┴────┴────┘
```

关键机制：

| 机制 | 作用 |
| --- | --- |
| RSet（Remembered Set） | 记录“谁指向我”，避免跨 Region 引用时扫描整个堆 |
| CSet（Collection Set） | 本次要回收的 Region 集合，优先回收垃圾最多的（Garbage First） |
| SATB | 并发标记时按“开始时快照”处理，保证不漏标 |
| `-XX:MaxGCPauseMillis` | 目标停顿时间，G1 据此挑选 CSet 大小 |

回收类型：**Young GC**（只回收新生代）、**Mixed GC**（新生代 + 部分老年代）、**Full GC**（单线程串行，兜底，应尽量避免）。

### ZGC

ZGC 用**染色指针**（在 64 位指针里借几位存标记信息）+ **读屏障**，把标记、转移、重定位都做成并发：

- JDK 11：实验特性，停顿约 10ms；
- JDK 15：转正；
- JDK 16：停顿降到 **1ms 以内**；
- JDK 21：**分代 ZGC**（JEP 439），解决“每次都要扫全堆”的问题。

代价是吞吐量略低于 G1，且需要更多内存余量（染色指针、转发表）。适合大堆（几十 GB 以上）、对停顿极敏感的服务。

## 六、什么时候触发 Full GC

| 触发条件 | 说明 |
| --- | --- |
| 老年代空间不足 | 晋升对象放不下 |
| 元空间不足 | 类加载过多（CMS 时代叫永久代满） |
| 空间分配担保失败 | Minor GC 前判断老年代放不下晋升对象 |
| `System.gc()` | 建议触发，可用 `-XX:+DisableExplicitGC` 忽略 |
| CMS 并发模式失败 | 预留空间不足，退化为 Serial Old |

## 七、面试连环问

**Q：怎么判断对象可以被回收？**

可达性分析：从 GC Roots 出发遍历，不可达的对象可回收。引用计数无法处理循环引用，Java 没有采用。

**Q：为什么分代？**

大部分对象朝生夕灭，少数长期存活。新生代用复制算法（存活少，复制成本低），老年代用标记-整理（存活多，避免浪费空间），各取所长。

**Q：Minor GC 和 Full GC 的区别？**

Minor GC 只回收新生代，频繁、快；Full GC 回收整堆（含元空间），慢、停顿长。Full GC 频繁通常意味着晋升过快或内存泄漏。

**Q：CMS 和 G1 的区别？**

CMS 只回收老年代、标记-清除有碎片、停顿不可预测；G1 面向整堆、Region 化、可设置目标停顿、整体是复制+标记整理（局部），碎片少。CMS 已在 JDK 14 移除。

**Q：G1 为什么能可预测停顿？**

它维护每个 Region 的回收价值（垃圾占比与回收成本），在 `MaxGCPauseMillis` 约束下挑选性价比最高的 Region 组成 CSet，而不是一次扫全堆。

**Q：ZGC 为什么停顿这么短？**

染色指针 + 读屏障把对象转移和引用修正都做成并发，STW 阶段只做根扫描等极少量工作。JDK 16 起把线程栈扫描也并发化，停顿进入亚毫秒级。

**Q：对象一定在 Eden 分配吗？**

不一定。大对象直接进老年代；TLAB 用尽且放不下会在 Eden 共享区分配；逃逸分析可能把对象**栈上分配**或**标量替换**，根本不进堆。
