# 28. CAP 理论

**一句话定位**：CAP 说的是——**当网络分区发生时**，系统只能在一致性（C）和可用性（A）之间选一个；P 不是可选项，是分布式系统的既成事实。

## 一、三个字母到底指什么

| 字母 | 含义 | 常见误解 |
| --- | --- | --- |
| C（Consistency） | **线性一致性**：任何时刻、任何节点读到的都是最新写入的值 | 误以为是一般的“数据一致”或“最终一致” |
| A（Availability） | **每个非故障节点**在有限时间内返回**非错误**响应 | 误以为“不宕机”就是 A，其实慢到超时也不算 A |
| P（Partition tolerance） | 网络分区时系统仍能继续工作 | 误以为 P 是“不会发生分区” |

关键点：**CAP 的 C 是强一致**，不是“主从最终同步”。很多系统号称“CA”，实际上只是“正常情况下看起来一致”。

## 二、为什么 P 必须选

分布式系统由多台机器组成，网络分区（丢包、延迟、交换机故障、机房断网）是**必然事件**，不是概率事件。你无法阻止两个节点失去联系，只能决定“失去联系后怎么办”。

所以真正的选择是：

```
分区发生时：
  ├── 选择 C：拒绝写入/阻塞等待，保证不会读到旧数据 → 牺牲可用性
  └── 选择 A：继续接受读写，可能返回旧数据     → 牺牲一致性
```

**没有分区时，C 和 A 可以同时满足**——这就是 CAP 最容易被误读的地方：不是“三选二”，而是“分区发生时在 C 和 A 里选一个”。

## 三、CP 与 AP

| 系统 | 类型 | 分区时的行为 |
| --- | --- | --- |
| ZooKeeper | CP | 少数派节点无法提供写服务，选举期间不可用 |
| etcd | CP | 依赖 Raft 多数派，少数派拒绝写入 |
| Redis Cluster（默认） | AP | 主从异步复制，主挂切换可能丢数据 |
| Eureka | AP | 节点间互相注册，分区时仍可读本地缓存 |
| Nacos | AP/CP 可配 | 临时实例用 AP（Distro），持久实例用 CP（Raft） |
| Consul | CP | 基于 Raft，强一致 |

一个常见误区：**ZooKeeper 是 CP，但不代表它“总是可用”**。选举期间（30~120 秒）整个集群可能无法写入，这正是它选择 C 的代价。

## 四、BASE：AP 的工程化表达

| 字母 | 含义 | 例子 |
| --- | --- | --- |
| BA（Basically Available） | 基本可用：允许损失部分可用性（降级、限流） | 大促时关闭非核心功能 |
| S（Soft state） | 软状态：允许中间状态存在 | 订单“支付中” |
| E（Eventually consistent） | 最终一致：经过一段时间后数据一致 | 主从延迟后最终同步 |

BASE 不是放弃一致性，而是**把“强一致”换成“最终一致 + 补偿”**，用业务手段兜底。

## 五、PACELC：CAP 的补充

CAP 只讨论“分区时”的选择，但系统大部分时间没有分区。PACELC 补上了这一点：

```
如果有分区（P）→ 在 A 和 C 之间选（A/C）
否则（E，Else）→ 在延迟（L）和一致性（C）之间选（L/C）
```

| 系统 | 分区时 | 正常时 |
| --- | --- | --- |
| DynamoDB | PA | EL（可用性优先，延迟低） |
| BigTable | PC | EC（一致性优先） |
| MongoDB | PC | EC |

这解释了一个现象：即使没有分区，主从异步复制也会为了低延迟牺牲强一致。

## 六、CAP 不能解决什么

CAP 是关于**分区期间**的理论，不告诉你：

- 分区恢复后怎么合并冲突（需要 CRDT、版本向量、业务对账）；
- 延迟和一致性怎么权衡（PACELC）；
- 业务上“一致”到底指什么（余额不能为负？订单不能重复？）。

所以工程上更常用的是**按业务分级**：

| 业务 | 一致性要求 | 方案 |
| --- | --- | --- |
| 支付扣款 | 强一致 | 数据库事务 + TCC |
| 库存扣减 | 强一致（防超卖） | 数据库行锁 / Redis Lua / 分布式锁 |
| 商品详情 | 最终一致 | 缓存 + 异步更新 |
| 点赞数、浏览量 | 弱一致 | 异步累加、定时校准 |

## 七、面试连环问

**Q：CAP 是什么？为什么只能三选二？**

一致性、可用性、分区容错性。分区是分布式系统无法避免的，所以 P 必选；分区发生时，要么拒绝服务保一致（CP），要么继续服务容忍不一致（AP）。没有分区时可以同时满足 C 和 A。

**Q：ZooKeeper 是 CP 还是 AP？**

CP。它基于 ZAB 协议，写操作需要过半节点确认；分区时少数派无法写入，选举期间不可用。

**Q：Eureka 为什么是 AP？**

Eureka 节点间异步复制注册信息，分区时各节点仍能提供查询和注册服务，代价是可能读到过期数据。它优先保证注册中心可用，因为“服务发现暂时不一致”比“整个服务不可用”更容易接受。

**Q：Nacos 是 CP 还是 AP？**

可配置。临时实例（`ephemeral=true`，默认）用 Distro 协议，是 AP；持久实例用 Raft，是 CP。大多数服务发现场景用 AP 就够了。

**Q：CAP 里的 C 和 ACID 里的 C 一样吗？**

不一样。CAP 的 C 是线性一致性（所有节点看到相同的顺序），ACID 的 C 是“约束不被破坏”（如余额不能为负、外键必须存在）。两者维度不同。

**Q：最终一致会不会丢数据？**

“最终一致”只保证“最终会一致”，不保证“中间不丢”。要防丢，需要：消息持久化 + 重试 + 幂等 + 对账。CAP 的 A 也不等于“数据不丢”，只是“有响应”。
