# 11. volatile

**一句话定位**：`volatile` 保证**可见性**和**有序性**（禁止指令重排），**不保证原子性**。它是最轻量的同步手段，适合“一个线程写、多个线程读”的状态标志。

## 一、两个语义

### 1. 可见性

普通变量的写先落在 CPU 缓存/Store Buffer 里，别的线程何时看到不确定。`volatile` 写会把值刷到主内存并使其他核心的缓存行失效，`volatile` 读会强制从主内存（或最新缓存）重新加载。

```java
public class VisibilityDemo {
    private static volatile boolean stop = false;

    public static void main(String[] args) throws Exception {
        new Thread(() -> {
            while (!stop) { /* 空转 */ }
            System.out.println("worker 退出");
        }).start();

        Thread.sleep(1000);
        stop = true;                 // 去掉 volatile，worker 可能永远不退出
    }
}
```

去掉 `volatile` 后，worker 线程可能把 `stop` 读到寄存器或工作内存里，JIT 甚至会把 `while (!stop)` 优化成死循环。加上 `volatile` 后每次循环都重新读取。

### 2. 有序性（禁止重排）

`volatile` 读写会插入内存屏障，禁止特定方向的指令重排：

| 屏障 | 作用 |
| --- | --- |
| LoadLoad | 禁止上面的普通读与下面的 `volatile` 读重排 |
| StoreStore | 禁止上面的普通写与下面的 `volatile` 写重排 |
| LoadStore | 禁止上面的 `volatile` 读与下面的普通写重排 |
| StoreLoad | 禁止上面的 `volatile` 写与下面的 `volatile` 读重排 |

JSR-133 Cookbook 给出的插入策略：

```
普通写 → [StoreStore] → volatile 写 → [StoreLoad] → ...
... → [LoadLoad] → volatile 读 → [LoadStore] → 普通读写
```

**StoreLoad 是最贵的屏障**，因为它要让写缓冲区排空、让其他核心看到最新值。x86 是 TSO（Total Store Order）模型，只允许 Store-Load 重排，所以：

- 其余三种屏障在 x86 上是**空操作**；
- `volatile` 写编译成 `lock addl $0, 0(ESP)`（HotSpot 的惯用手法），`lock` 前缀自带全屏障语义；也可以理解成 `mfence`。

这就是“x86 上 volatile 几乎是免费的”这个说法的来源——只有写操作有真实指令，读操作只是禁止编译器重排。

## 二、为什么不保证原子性

```java
private volatile int count = 0;

public void inc() {
    count++;      // 不是原子操作
}
```

`count++` 的字节码：

```text
aload_0
dup
getfield      # count      // ① 读
iconst_1
iadd                       // ② 加
putfield      # count      // ③ 写
```

两个线程可能同时读到 0，各自加 1 后都写回 1，最终结果是 1 而不是 2。`volatile` 只保证“读到的值是最新的”，不保证“读-改-写”这一整段不被打断。

需要原子性时用 `AtomicInteger`（CAS）或 `synchronized`。

## 三、volatile 与 happens-before

JMM 里有一条规则：**对一个 `volatile` 变量的写，happens-before 后续对同一变量的读**。

这意味着写线程在 `volatile 写` 之前的**所有普通写**，对读线程在 `volatile 读` 之后都是可见的。这就是“一次性安全发布”的基础：

```java
public class Config {
    private int a, b, c;
    private volatile boolean initialized = false;

    public void init() {
        a = 1; b = 2; c = 3;          // 普通写
        initialized = true;            // volatile 写，前面的写都被“发布”
    }

    public void use() {
        if (initialized) {             // volatile 读
            System.out.println(a + b + c);   // 一定能看到 1、2、3
        }
    }
}
```

::: tip
注意方向性：**volatile 写之前**的写会被发布，**volatile 读之后**的读能看到这些写。反过来不成立。

:::

## 四、双重检查锁（DCL）

```java
public class Singleton {
    private static volatile Singleton instance;

    public static Singleton getInstance() {
        if (instance == null) {                    // 第一次检查，避免每次都加锁
            synchronized (Singleton.class) {
                if (instance == null) {            // 第二次检查，防止重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

`instance = new Singleton()` 分三步：

```text
① 分配内存
② 调用构造器初始化对象
③ 把引用赋值给 instance
```

②③ 之间没有数据依赖，JIT/CPU 可能重排成 ①③②。此时另一个线程在第一次检查时看到 `instance != null`，拿到的是一个**构造器还没执行完的对象**，字段全是默认值——经典的“半初始化对象”问题。

`volatile` 禁止 ②③ 重排，保证读到非 null 时对象一定初始化完成。

补充：如果不允许 `volatile`（比如老代码），静态内部类写法更简洁：

```java
public class Singleton {
    private static class Holder {
        static final Singleton INSTANCE = new Singleton();
    }
    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```

类加载机制保证 `Holder` 只初始化一次，且延迟到第一次调用 `getInstance()`。

## 五、适用与不适用

| 场景 | 是否适用 | 说明 |
| --- | --- | --- |
| 状态标志（`volatile boolean running`） | ✅ | 一个线程写、多个线程读，不需要原子性 |
| 一次性安全发布（上面的 `initialized`） | ✅ | 配合 happens-before 使用 |
| DCL 单例 | ✅ | 防止半初始化对象 |
| 计数器（`count++`） | ❌ | 读-改-写，需要 CAS 或锁 |
| 多个变量要保持一致 | ❌ | 单变量可见性无法保证组合操作的原子性 |
| 作为锁使用 | ❌ | `volatile` 不提供互斥 |

## 六、volatile、synchronized、Atomic 怎么选

| 需求 | 选择 |
| --- | --- |
| 只保证可见性/有序性，单写多读 | `volatile` |
| 单个变量的原子读-改-写 | `AtomicInteger` / `LongAdder` |
| 多个变量、复合操作、需要互斥 | `synchronized` / `ReentrantLock` |
| 高并发计数 | `LongAdder`（分散热点） |

一句话：**`volatile` 解决“看不看得见”，`synchronized` 解决“能不能同时做”，CAS 解决“单个变量的原子更新”**。

## 七、常见误解

**误解一：`volatile` 变量在所有 CPU 上都会实时同步。**

现代 CPU 有 Store Buffer 和无效队列，`volatile` 的保证是**顺序一致性语义**（对 volatile 变量本身），实现靠屏障，不是“每条指令都写内存”。理解成“写到主内存”是简化模型，够面试用，但别拿它推导性能。

**误解二：`volatile` 数组的元素也是 volatile。**

`volatile int[] arr` 只保证**数组引用**的可见性，`arr[0] = 1` 不是 volatile 写。需要元素级可见性用 `AtomicIntegerArray`。

**误解三：`volatile` 能替代锁。**

::: warning
它不提供互斥。两个线程同时 `volatileVar++`，结果照样丢更新。

:::

**误解四：加了 `volatile` 就一定不会重排。**

只禁止**与 volatile 变量相关**的特定方向重排，两个普通变量之间的重排不受影响。

## 八、面试连环问

**Q：volatile 的底层实现？**

写：StoreStore 屏障 + volatile 写 + StoreLoad 屏障；读：LoadLoad 屏障 + volatile 读 + LoadStore 屏障。x86 上只有 StoreLoad 需要真实指令（`lock` 前缀），其余是编译器层面的约束。

**Q：volatile 能保证原子性吗？**

不能。`i++` 是读-改-写三步，`volatile` 只保证每一步读到最新值，不保证三步整体不被打断。

**Q：DCL 为什么必须加 volatile？**

`new` 的“分配内存、初始化、赋值引用”可能重排成“分配、赋值、初始化”，其他线程会拿到未初始化完成的对象。`volatile` 禁止这个重排。

**Q：volatile 和 synchronized 的区别？**

`volatile` 轻量、只保证可见性和有序性、不互斥、不阻塞；`synchronized` 重量、互斥、保证可见性和原子性、可能阻塞。能用 volatile 就不用锁。

**Q：volatile 读和普通读性能差多少？**

x86 上 volatile 读几乎没有额外指令（只是禁止编译器重排），volatile 写多一条 `lock` 前缀指令。整体开销远小于锁，但不能滥用——大量 volatile 写会持续让缓存行失效，反而拖慢多核性能。

**Q：final 和 volatile 的关系？**

`final` 字段也有“安全发布”语义：构造器中对 final 字段的写，happens-before 其他线程读到该对象引用之后的读。正确构造的不可变对象（所有字段 final）不需要 volatile 也能安全发布。前提是**构造期间 this 没有逃逸**。
