# 14. CAS 与 ABA

**一句话定位**：CAS（Compare-And-Swap）是 CPU 提供的一条**原子指令**：“如果内存里的值还等于期望值，就把它改成新值”，是自旋锁、原子类、AQS 的共同底座。

## 一、CAS 的三个操作数与语义

```text
CAS(V, A, B)
V：要读写的内存地址
A：期望的旧值（Expected）
B：准备写入的新值（New）

执行：原子地比较 V 处的值是否等于 A
     ├── 相等 → 把 V 改成 B，返回 true
     └── 不相等 → 什么都不做，返回 false（调用方通常重试）
```

“比较 + 交换”这两步在硬件层面是一条指令（x86 的 `lock cmpxchg`），不会被其他核心插入，所以不需要加锁。

Java 里最原始的入口是 `Unsafe`：

```java
public final native boolean compareAndSwapInt(Object o, long offset, int expected, int x);
```

JDK 9 之后更推荐 `VarHandle`：

```java
private static final VarHandle STATE;
static {
    try {
        STATE = MethodHandles.lookup().findVarHandle(MyClass.class, "state", int.class);
    } catch (ReflectiveOperationException e) {
        throw new ExceptionInInitializerError(e);
    }
}

boolean ok = STATE.compareAndSet(this, expect, update);
```

## 二、AtomicInteger 的自旋

```java
public final int getAndIncrement() {
    return unsafe.getAndAddInt(this, valueOffset, 1);
}

// Unsafe 内部
public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = getIntVolatile(o, offset);       // 读当前值
    } while (!compareAndSwapInt(o, offset, v, v + delta));   // CAS 失败就重试
    return v;
}
```

`valueOffset` 是 `value` 字段在对象内存中的偏移量，`getIntVolatile` 保证读到的是最新值。整个方法是**乐观**的：不阻塞，失败了重来。低竞争时比锁快得多；高竞争时大量线程原地打转，反而浪费 CPU。

## 三、ABA 问题

```text
线程 1 读到 value = A
线程 2 把 A 改成 B，又改回 A
线程 1 执行 CAS(A, C) → 成功
```

线程 1 以为“值没变过”，实际上中间已经被改过两次。对 `int` 计数来说无所谓（加减有交换律），但对**依赖中间状态的对象**来说会出问题：

```java
// 用 CAS 实现的栈
Stack: top → A → B → C
线程 1：读到 top = A，准备 CAS(top, A, B)     // 想弹栈
线程 2：弹出 A、弹出 B、又压回 A
线程 1：CAS 成功，top 变成 B —— 但 B 已经被弹出并可能被回收
结果：top 指向一个已失效的节点
```

### 解决：版本号

```java
AtomicStampedReference<Integer> ref = new AtomicStampedReference<>(100, 0);

int stamp = ref.getStamp();                       // 读当前版本号
boolean ok = ref.compareAndSet(100, 200, stamp, stamp + 1);
```

`AtomicStampedReference` 内部把“引用 + int 版本号”打包成一个 `Pair`，CAS 时两个字段一起比较，A→B→A 的版本号已经从 0 变成 2，CAS 会失败。

另一个选择是 `AtomicMarkableReference`，只带一个 boolean 标记（适合“是否被删除”这种二值状态）。

## 四、CAS 的三个缺点

| 缺点 | 说明 | 对策 |
| --- | --- | --- |
| 自旋开销 | 高竞争下大量线程空转，CPU 占用高 | 限制自旋次数、退化为锁、用 `LongAdder` 分散热点 |
| 只能保证单个变量 | 无法一次原子更新多个变量 | 打包成对象用 `AtomicReference`，或加锁 |
| ABA 问题 | 值改回原样，CAS 察觉不到 | 版本号 `AtomicStampedReference` |

## 五、LongAdder：把热点拆开

`AtomicLong` 在高并发下所有线程 CAS 同一个 `value`，失败率极高。`LongAdder` 继承 `Striped64`，思路是**分散**：

```
          base
            │
   ┌────────┼────────┐
 Cell[0]  Cell[1]  Cell[2] ...      ← 每个线程按 probe 散列到不同槽，各自 CAS
```

- 低竞争：直接 CAS `base`；
- 高竞争：扩容 `Cell[]`，线程各自累加自己的槽；
- `sum()`：把 `base` 和所有 `Cell` 加起来（**不是原子快照**）。

| 维度 | AtomicLong | LongAdder |
| --- | --- | --- |
| 写性能 | 高竞争下差 | 好（分散热点） |
| 读性能 | O(1) | O(n)，要遍历 Cell |
| 结果精度 | 精确 | `sum()` 是近似值 |
| 适用 | 读写均衡、要求精确 | 写多读少（如 QPS 统计） |

## 六、CAS 与锁的对比

| 维度 | CAS | 锁 |
| --- | --- | --- |
| 策略 | 乐观：先改，冲突再重试 | 悲观：先占住，别人等着 |
| 阻塞 | 不阻塞（自旋） | 可能阻塞、线程挂起 |
| 适用 | 竞争不激烈、临界区极短 | 竞争激烈、临界区长 |
| 问题 | 自旋耗 CPU、ABA、单变量 | 上下文切换、死锁风险 |

实际系统里两者经常组合：`ConcurrentHashMap` 空桶用 CAS、非空桶用 `synchronized`；AQS 用 CAS 改 state、用 park 阻塞。

## 七、面试连环问

**Q：CAS 的原理？**

三个操作数 V/A/B，硬件用一条原子指令完成“比较并交换”。Java 通过 `Unsafe.compareAndSwapInt` 或 `VarHandle.compareAndSet` 调用，失败返回 false，调用方自旋重试。

**Q：CAS 怎么保证原子性？**

靠 CPU 指令。x86 是 `lock cmpxchg`，`lock` 前缀会锁总线或缓存行，保证比较和交换之间没有其他核心插入。不是靠 Java 层面的同步。

**Q：ABA 是什么？怎么解决？**

值从 A 改成 B 又改回 A，CAS 只比较当前值，察觉不到中间变化。解决是加版本号（`AtomicStampedReference`）或标记（`AtomicMarkableReference`），把“值 + 版本”一起 CAS。

**Q：CAS 有什么缺点？**

自旋开销大（高竞争时空转）、只能保证单个变量、存在 ABA。分别用退避/锁、`AtomicReference` 打包、版本号解决。

**Q：AtomicInteger 和 synchronized 怎么选？**

单变量计数、竞争不激烈用 `AtomicInteger`；需要多个变量一起原子更新、或者临界区里有复杂逻辑，用 `synchronized`。高并发计数优先 `LongAdder`。

**Q：CAS 能替代锁吗？**

不能完全替代。CAS 只适合“读-比较-写”的单变量场景；涉及多个共享变量的不变式时，CAS 无法保证整体原子性，还是要靠锁。
