# 31. 单例模式

**一句话定位**：单例保证一个类**只有一个实例**并提供全局访问点；真正要解决的是“懒加载 + 线程安全 + 防反射/序列化破坏”这三件事。

## 一、五种写法

### 1. 饿汉式

```java
public class Singleton {
    private static final Singleton INSTANCE = new Singleton();
    private Singleton() {}
    public static Singleton getInstance() { return INSTANCE; }
}
```

类加载时就创建，**线程安全**（`<clinit>` 由 JVM 保证只执行一次），实现最简单。缺点是不管用不用都占内存；如果构造器依赖外部配置，初始化顺序不好控制。

### 2. 懒汉式（同步方法）

```java
public class Singleton {
    private static Singleton instance;
    private Singleton() {}
    public static synchronized Singleton getInstance() {
        if (instance == null) instance = new Singleton();
        return instance;
    }
}
```

第一次调用才创建，但**每次调用都加锁**，并发下性能差。不推荐。

### 3. 双重检查锁（DCL）

```java
public class Singleton {
    private static volatile Singleton instance;      // 必须 volatile

    private Singleton() {}

    public static Singleton getInstance() {
        if (instance == null) {                       // 第一次检查：避免每次都加锁
            synchronized (Singleton.class) {
                if (instance == null) {               // 第二次检查：防止重复创建
                    instance = new Singleton();
                }
            }
        }
        return instance;
    }
}
```

### 4. 静态内部类（推荐）

```java
public class Singleton {
    private Singleton() {}

    private static class Holder {
        private static final Singleton INSTANCE = new Singleton();
    }

    public static Singleton getInstance() { return Holder.INSTANCE; }
}
```

- 懒加载：`Holder` 只在第一次调用 `getInstance()` 时初始化；
- 线程安全：`<clinit>` 由 JVM 加锁保证只执行一次；
- 无锁开销：初始化完成后直接返回静态字段。

这是**最推荐的写法**——兼顾懒加载、线程安全和简洁。

### 5. 枚举（防反射/序列化破坏）

```java
public enum Singleton {
    INSTANCE;

    public void doSomething() { /* ... */ }
}
```

`《Effective Java》` 作者 Josh Bloch 推荐。JVM 保证枚举实例唯一，且**天然防反射、防序列化破坏**。缺点是做不到懒加载（枚举类加载时就创建），继承场景受限。

## 二、DCL 为什么必须 volatile

`instance = new Singleton()` 对应三条指令：

```text
① memory = allocate()        // 分配内存
② ctorInstance(memory)       // 调用构造器初始化
③ instance = memory          // 把引用指向内存
```

②③ 之间没有数据依赖，JIT/CPU 可能重排成 ①③②。此时另一个线程在第一次检查时看到 `instance != null`，拿到的是一个**构造器还没执行完的对象**——字段全是默认值。

`volatile` 禁止这个重排（在 ③ 之前插入 StoreStore 屏障），保证“看到非 null 时对象一定初始化完成”。

## 三、五种写法对比

| 写法 | 懒加载 | 线程安全 | 性能 | 防反射 | 防序列化 |
| --- | --- | --- | --- | --- | --- |
| 饿汉式 | ❌ | ✅ | 高 | ❌ | ❌ |
| 懒汉式（同步方法） | ✅ | ✅ | 低 | ❌ | ❌ |
| DCL | ✅ | ✅（需 volatile） | 高 | ❌ | ❌ |
| 静态内部类 | ✅ | ✅ | 高 | ❌ | ❌ |
| 枚举 | ❌ | ✅ | 高 | ✅ | ✅ |

## 四、怎么破坏单例

### 反射

```java
Constructor<Singleton> ctor = Singleton.class.getDeclaredConstructor();
ctor.setAccessible(true);
Singleton s1 = ctor.newInstance();
Singleton s2 = ctor.newInstance();     // 两个不同实例
```

防护：构造器里判断实例是否已存在，存在则抛异常：

```java
private Singleton() {
    if (Holder.INSTANCE != null) throw new IllegalStateException("单例已被破坏");
}
```

但这种方式在类初始化顺序上很脆弱，枚举才是彻底方案。

### 序列化

反序列化会通过反射创建新对象，绕过构造器：

```java
private Object readResolve() {
    return Holder.INSTANCE;      // 返回已有实例，丢弃反序列化出来的新对象
}
```

### 克隆

实现 `Cloneable` 后 `clone()` 会创建新对象。防护：不实现 `Cloneable`，或重写 `clone()` 返回 `INSTANCE`。

### 枚举为什么防得住

- 反射：`Constructor.newInstance` 对枚举类直接抛 `IllegalArgumentException: Cannot reflectively create enum objects`；
- 序列化：枚举的序列化由 JVM 特殊处理，反序列化返回同一个实例，不走构造器。

## 五、单例在框架里的样子

| 场景 | 实现方式 |
| --- | --- |
| Spring 单例 Bean | 容器内一个实例，存在 `singletonObjects` 缓存 |
| 数据库连接池 | 全局唯一，通常用枚举或静态内部类 |
| 配置管理器 | 静态内部类 + 不可变配置 |
| 日志器 | 通常由框架管理，不自己写单例 |

::: info
**Spring 的单例 Bean 不等于设计模式里的单例**。Spring 的单例是“容器内一个实例”，你仍然可以 `new` 出第二个对象；设计模式的单例是“JVM 内一个实例”，构造器私有。

:::

## 六、面试连环问

**Q：DCL 为什么需要 volatile？**

`new` 的“分配内存、初始化、赋值引用”可能重排，导致其他线程拿到未初始化完成的对象。`volatile` 禁止 ②③ 重排。

**Q：静态内部类为什么能保证线程安全？**

`Holder` 的初始化由 JVM 的类初始化机制保证，`<clinit>` 在多线程下会被加锁，只有一个线程执行，其他线程阻塞等待。

**Q：枚举单例为什么是最佳实践？**

JVM 保证枚举实例唯一，反射无法创建枚举实例，序列化返回同一对象。代码也最短。

**Q：单例有什么缺点？**

隐藏依赖（全局状态）、难以单测（需要重置状态）、并发下可能成为瓶颈、生命周期难管理。现代框架更倾向用依赖注入管理“单例作用域”的 Bean，而不是手写单例。

**Q：如何防止反射破坏单例？**

构造器中检查实例是否已存在并抛异常；更彻底的是用枚举。注意 `setAccessible(true)` 能突破 private，所以“私有构造器”本身不是防护。
