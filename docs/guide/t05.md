# 5. 异常体系

**一句话定位**：异常体系回答三个问题——**哪些异常必须处理**（checked）、**哪些是程序 bug**（RuntimeException）、**哪些根本不该处理**（Error）。

## 一、整体结构

```
Throwable
├── Error                         不该 catch，程序已处于不可恢复状态
│   ├── OutOfMemoryError
│   ├── StackOverflowError
│   ├── NoClassDefFoundError
│   └── VirtualMachineError
└── Exception
    ├── RuntimeException          unchecked，编译器不强制处理
    │   ├── NullPointerException
    │   ├── ArithmeticException
    │   ├── ClassCastException
    │   ├── ArrayIndexOutOfBoundsException
    │   └── IllegalArgumentException
    └── 其他 Exception             checked，编译期必须 catch 或 throws
        ├── IOException
        │   └── FileNotFoundException
        ├── SQLException
        ├── ClassNotFoundException
        └── InterruptedException
```

判断口径只有一条：**`RuntimeException` 及其子类、`Error` 及其子类是 unchecked，其余 `Exception` 子类是 checked**。

## 二、三类异常的处理姿势

| 类型 | 代表 | 该不该 catch | 正确姿势 |
| --- | --- | --- | --- |
| Error | `OutOfMemoryError` | 一般不要 | 让它冒泡，修复内存/栈配置或代码，不要 `catch (Throwable)` 一把抓 |
| RuntimeException | `NullPointerException`、`IllegalArgumentException` | 不强制，但边界处要转 | 参数校验失败就提前抛，别让它带着无意义的空指针跑到深处 |
| checked Exception | `IOException`、`SQLException` | 必须处理 | 能恢复就恢复，不能恢复就包装成业务异常往上抛 |

`Error` 里有一个例外值得知道：`OutOfMemoryError` 在个别场景可以被捕获后释放资源再退出，但捕获后继续提供服务基本等于自欺欺人。

## 三、finally 与 return 的执行顺序

这是最高频的笔试题。结论：**`finally` 一定会执行（除非 JVM 退出或线程被杀），且 `finally` 里的 `return` 会覆盖 `try` 里的 `return`**。

```java
static int f() {
    int x = 1;
    try {
        return x;          // ① 计算返回值 1，暂存
    } finally {
        x = 2;             // ② 修改局部变量，但返回值已经定好了
    }
}
// 返回 1，不是 2
```

```java
static int g() {
    try {
        return 1;
    } finally {
        return 2;          // 直接覆盖，返回 2
    }
}
```

原因在字节码层面：`javac` 会把 `finally` 块**复制**到 try 的正常出口和每个 catch 出口，`return` 的表达式在进入 `finally` 之前就已经求值并存入局部变量槽。所以：

- `finally` 里改基本类型的局部变量，不影响已确定的返回值；
- `finally` 里改引用对象的字段，会影响返回值（因为返回的是引用）；
- `finally` 里的 `return` 会丢弃 try 中的返回值和异常。

::: danger
工程上有一条硬规则：**不要在 `finally` 里写 `return`**，否则异常会被吞掉：

```java
try {
    throw new RuntimeException("boom");
} finally {
    return;      // 异常被丢弃，方法正常返回
}
```

:::

## 四、try-with-resources

Java 7 引入，资源必须实现 `AutoCloseable`（`Closeable` 是它的子接口）：

```java
try (Connection conn = dataSource.getConnection();
     PreparedStatement ps = conn.prepareStatement(sql)) {
    ps.execute();
}
```

脱糖后大致等价于：

```java
Connection conn = null;
Throwable primary = null;
try {
    conn = dataSource.getConnection();
    // 业务
} catch (Throwable t) {
    primary = t;
    throw t;
} finally {
    if (conn != null) {
        if (primary != null) {
            try { conn.close(); }
            catch (Throwable suppressed) { primary.addSuppressed(suppressed); }
        } else {
            conn.close();
        }
    }
}
```

关键点：**关闭时抛出的异常不会覆盖主异常，而是挂到 `suppressed` 数组里**，用 `getSuppressed()` 查看。手写 `finally { close(); }` 做不到这一点——`close()` 一抛，业务异常就丢了。

声明顺序决定关闭顺序：**后声明的先关闭**（栈式）。

## 五、异常的性能

创建异常的开销几乎全在 `fillInStackTrace()`——它要遍历当前线程的整个调用栈。所以：

| 做法 | 效果 |
| --- | --- |
| 复用同一个异常实例 | 栈信息停留在创建时，排查困难，不推荐 |
| 重写 `fillInStackTrace()` 返回 `this` | 去掉栈填充，适合“控制流异常”（如 `NumberFormatException` 的高频路径） |
| JIT 优化 | 同一个异常点反复抛出时，JIT 会做栈省略（stack trace elision），但依赖逃逸分析，不能当成设计依据 |

结论：异常不该用于正常控制流。用异常做循环退出条件，比 `if` 慢一到两个数量级。

## 六、自定义异常与包装

```java
public class OrderNotFoundException extends RuntimeException {
    private final long orderId;

    public OrderNotFoundException(long orderId) {
        super("order not found: " + orderId);
        this.orderId = orderId;
    }
}
```

三条经验：

1. **业务异常继承 `RuntimeException`**，避免污染方法签名；跨层时由全局异常处理器统一转成错误码。
2. **包装要保留 cause**：`throw new ServiceException("下单失败", e)`，不要 `throw new ServiceException(e.getMessage())`——后者丢栈，线上只能看到一句没有上下文的字符串。
3. **不要 catch 了什么都不做**。至少记日志；更常见的是 catch 后原样抛出，此时不如不 catch。

## 七、面试连环问

**Q：checked 和 unchecked 的本质区别？**

编译器是否强制处理。checked 异常是“调用者可能恢复的外部故障”（文件不存在、网络断开），语言用编译期检查逼你面对；unchecked 是“程序写错了”（空指针、越界），暴露得越早越好，不需要在每个调用点声明。

**Q：`catch (Exception e)` 和 `catch (Throwable t)` 有什么区别？**

`Exception` 不含 `Error`；`Throwable` 两者都抓。抓 `Throwable` 会把 `OutOfMemoryError`、`ThreadDeath` 一起吞掉，通常只在最外层的兜底日志、或者框架的线程池 worker 里出现。

**Q：`finalize` 能用来释放资源吗？**

不能依赖。执行时机不确定、可能不执行、吞异常、拖慢 GC（需要额外的 finalizer 队列），JDK 9 起标记废弃，JDK 18 起 `finalization` 默认关闭（JEP 421）。用 try-with-resources 或 `Cleaner`。

**Q：`throw` 和 `throws` 的区别？**

`throw` 是语句，抛出一个异常实例；`throws` 是方法声明，告诉调用者“我可能抛这些异常”。`throws` 只对 checked 异常有强制力。

**Q：异常表是什么？**

方法字节码里的 `Exception table`，每行是 `[start_pc, end_pc, handler_pc, catch_type]`。JVM 靠它做异常分派，没有 `catch` 的方法不会有对应表项。`finally` 的“复制”就是靠多个 handler 指向同一段代码实现的。
