# 23. 缓存穿透、缓存击穿、缓存雪崩

**一句话定位**：三者都是“请求绕过缓存打到 DB”，区别只在**原因**——查不存在的数据（穿透）、单个热点 key 失效（击穿）、大量 key 同时失效或 Redis 挂掉（雪崩）。

## 一、对比总表

| 问题 | 触发原因 | 现象 | 解决 |
| --- | --- | --- | --- |
| 缓存穿透 | 查询**根本不存在**的数据，缓存永远不命中 | 恶意 ID 刷接口，DB 压力持续升高 | 布隆过滤器、缓存空值、参数校验、限流 |
| 缓存击穿 | **单个热点 key** 过期瞬间，大量并发同时未命中 | 某一时刻 DB QPS 突增 | 互斥锁重建、逻辑过期、热点永不过期 |
| 缓存雪崩 | **大量 key 同时过期**，或 Redis 整体不可用 | DB 瞬间被打满，甚至连锁宕机 | TTL 加随机值、高可用集群、限流降级、多级缓存 |

记忆：**穿透是“查不到”，击穿是“一个没了”，雪崩是“一片没了”**。

## 二、缓存穿透

### 方案一：缓存空值

查不到也缓存一个特殊值（如 `""` 或 `NULL` 标记），TTL 设短（30~60 秒）：

```java
public String get(String key) {
    String value = redis.opsForValue().get(key);
    if (value != null) {
        return NULL_MARK.equals(value) ? null : value;
    }

    value = db.query(key);
    if (value == null) {
        redis.opsForValue().set(key, NULL_MARK, 60, TimeUnit.SECONDS);   // 短 TTL，防止脏数据长期占用
        return null;
    }
    redis.opsForValue().set(key, value, 30, TimeUnit.MINUTES);
    return value;
}
```

优点：实现简单。缺点：大量随机不存在的 key 会占用内存（每个空值也要存），且数据新增后有短暂不一致。

### 方案二：布隆过滤器

在缓存之前加一层布隆过滤器，判断“这个 key 一定不存在”时直接返回：

```
请求 → 布隆过滤器
        ├── 不存在（一定不存在）→ 直接返回 null
        └── 可能存在 → 查 Redis → 未命中 → 查 DB
```

布隆过滤器 = 一个 bit 数组 + 多个哈希函数：

```text
添加 "user:1"：
  hash1("user:1") % m → 位置 3，置 1
  hash2("user:1") % m → 位置 17，置 1
  hash3("user:1") % m → 位置 42，置 1

查询 "user:1"：三个位置都是 1 → 可能存在
查询 "user:999"：位置 5 是 0 → 一定不存在
```

| 特性 | 说明 |
| --- | --- |
| 误判 | 可能把不存在的判为存在（哈希碰撞），但不会把存在的判为不存在 |
| 删除 | 不支持（置 0 会影响其他 key），要用 Counting Bloom Filter 或定期重建 |
| 参数 | 位数组越大、哈希函数越多，误判率越低，内存和 CPU 成本越高 |

Guava 的 `BloomFilter` 或 Redis 的 `BF.ADD` / `BF.EXISTS`（RedisBloom 模块）都可以直接用。

### 方案三：前置校验

- ID 格式校验（负数、超长、非数字直接拒绝）；
- 用户权限校验（只能查自己的订单）；
- 接口限流（同一 IP/用户的异常请求频率）。

穿透往往是**攻击行为**，光靠缓存层兜不住，入口必须挡。

## 三、缓存击穿

### 方案一：互斥锁重建

只让一个线程去查 DB 并回填，其余线程等待后重试：

```java
public String get(String key) {
    String value = redis.opsForValue().get(key);
    if (value != null) return value;

    String lockKey = "lock:" + key;
    String token = UUID.randomUUID().toString();
    // SET key value NX PX 3000 —— 加锁和过期必须一条命令完成
    Boolean locked = redis.opsForValue().setIfAbsent(lockKey, token, 3, TimeUnit.SECONDS);

    if (Boolean.TRUE.equals(locked)) {
        try {
            value = redis.opsForValue().get(key);          // 双重检查：可能别的线程已经回填
            if (value != null) return value;

            value = db.query(key);
            redis.opsForValue().set(key, value, 30, TimeUnit.MINUTES);
            return value;
        } finally {
            // Lua 比对 token 再删，防止误删别人的锁
            String lua = "if redis.call('get', KEYS[1]) == ARGV[1] then " +
                         "return redis.call('del', KEYS[1]) else return 0 end";
            redis.execute(new DefaultRedisScript<>(lua, Long.class),
                          Collections.singletonList(lockKey), token);
        }
    }

    Thread.sleep(50);                         // 没抢到锁，短暂等待后重试
    return get(key);
}
```

要点：

1. **加锁必须带过期时间**，否则持锁线程挂掉会永久死锁；
2. **释放锁必须校验 token**，否则可能删掉别人的锁（见 [26. 分布式锁](/guide/t26)）；
3. **递归重试要有次数上限**，否则 DB 长时间不可用时会无限递归。

### 方案二：逻辑过期

key 不设物理 TTL，值里带一个过期时间戳：

```java
class CacheValue {
    Object data;
    long expireAt;       // 逻辑过期时间
}

public Object get(String key) {
    CacheValue cv = (CacheValue) redis.opsForValue().get(key);   // 实际项目中用带类型的 RedisTemplate
    if (cv == null) return loadAndSet(key);          // 冷启动

    if (cv.expireAt > System.currentTimeMillis()) {
        return cv.data;                              // 未过期，直接返回
    }

    // 已逻辑过期：尝试拿锁异步重建，拿不到也返回旧值
    Boolean locked = redis.opsForValue().setIfAbsent("lock:" + key, "1", 3, TimeUnit.SECONDS);
    if (Boolean.TRUE.equals(locked)) {
        asyncExecutor.execute(() -> {
            try {
                CacheValue fresh = loadFromDb(key);
                redis.opsForValue().set(key, fresh);               // 不设物理过期
            } finally {
                redis.del("lock:" + key);
            }
        });
    }
    return cv.data;                                  // 先返回旧值，保证可用性
}
```

优点：请求永远不会阻塞，可用性高。缺点：会短暂返回旧数据，适合“可容忍短暂不一致”的热点数据（商品详情、配置）。

### 方案三：热点 key 永不过期

后台定时刷新，物理上不设 TTL。适合可枚举的少量热点（首页 banner、秒杀商品），不适合海量 key。

## 四、缓存雪崩

### 方案一：TTL 打散

在基础 TTL 上加随机值，避免同一时刻集体过期：

```java
int ttl = 30 * 60 + ThreadLocalRandom.current().nextInt(5 * 60);   // 30~35 分钟
redis.set(key, value, ttl, TimeUnit.SECONDS);
```

### 方案二：高可用

- Redis 主从 + 哨兵，或 Cluster 集群；
- 本地缓存做二级缓存（Caffeine），Redis 挂了还有一层；
- 熔断降级：Redis 不可用时直接返回兜底数据或限流，不要全量打到 DB。

### 方案三：限流 + 预热

- 大促前预热热点数据，避免开服瞬间全部未命中；
- 网关/服务层限流，DB 前面加一层保护；
- 缓存重建用队列串行化，避免并发重建压垮 DB。

## 五、三者会互相转化

- 击穿处理不好（大量热点 key 同时过期）→ 变成雪崩；
- 穿透没拦（攻击流量持续）→ DB 连接池耗尽 → 影响其他接口 → 近似雪崩；
- 雪崩时大量请求穿透到 DB，DB 慢了，缓存重建更慢，形成正反馈。

所以生产上通常是**组合拳**：布隆过滤器 + 空值缓存 + 随机 TTL + 互斥重建 + 多级缓存 + 限流降级。

## 六、面试连环问

**Q：缓存穿透、击穿、雪崩的区别？**

穿透是查不存在的数据（缓存和 DB 都没有）；击穿是单个热点 key 失效瞬间大量请求打到 DB；雪崩是大量 key 同时失效或 Redis 整体故障。前两者是“key 的问题”，后者是“面”的问题。

**Q：布隆过滤器为什么不能删除元素？**

一个 bit 可能被多个元素共享，置 0 会把其他元素的判断也改掉，造成“存在的被判为不存在”。需要删除时用 Counting Bloom Filter（每个位置计数）或定期重建。

**Q：布隆过滤器会误判吗？**

会，但只有假阳性（不存在的判为存在），没有假阴性（存在的不会判为不存在）。所以它适合做“前置拦截”，不能做“唯一性判断”。

**Q：互斥锁方案和逻辑过期怎么选？**

要求强一致、能接受短暂阻塞 → 互斥锁；要求高可用、能接受短暂旧数据 → 逻辑过期。秒杀类场景常用逻辑过期，商品详情这类读多写少也适合。

**Q：为什么缓存空值要设短 TTL？**

防止“当时不存在、后来新增”的数据被空值长期挡住。短 TTL 是一个折中：既挡住了大部分重复穿透，又能在数据新增后较快恢复。

**Q：Redis 挂了怎么办？**

本地缓存兜底 + 限流 + 降级返回默认值，同时尽快恢复 Redis。不要在 Redis 故障时让所有请求直连 DB，那会把 DB 一起打挂。
