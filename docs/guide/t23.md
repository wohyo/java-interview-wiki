# 23. 缓存穿透、缓存击穿、缓存雪崩

**Q：缓存穿透、击穿、雪崩分别是什么？怎么解决？**

三者的区别在于"打到 DB 的原因"不同。

缓存穿透查的是根本不存在的数据，缓存里永远不会有，请求每次都落到 DB，常见来源是拿不存在的 ID 恶意刷。两条路：用布隆过滤器在入口拦掉一定不存在的 key；或者把"查不到"这个结果也缓存起来（空值，TTL 设短一点）。

缓存击穿是单个热点 key 到期的那一瞬间，大量并发请求同时未命中，一起压向 DB。解决是加互斥锁——只放一个线程去查 DB 并回填，其余线程等待重试（SETNX，下面有代码）；或者用逻辑过期，key 不设物理 TTL，值里带一个时间戳，发现过期后由异步线程更新，读请求照常命中旧值。

缓存雪崩是大量 key 在同一时刻集体过期，或者 Redis 整个宕机，DB 瞬间承受全部流量。四层一起兜：TTL 加随机值把过期时间打散；上集群/主从避免单点；入口限流加服务降级；再加一层本地缓存（多级缓存），Redis 挂了还有 Caffeine 挡一下。

**🔥 Q：布隆过滤器的原理和缺点？**

原理：一个超大的 bit 数组 + 多个哈希函数。添加 key 时将多个 hash 位置 1。查询时如果任一hash 位为 0 → 一定不存在（可拦截穿透）

缺点：存在误判率（可能把一个不存在的 key 判为存在）→ 少量穿透仍可能发生。不支持删除

误判率调整：增加 bit 数组大小和哈希函数数量可降低误判率，但增加内存

**🔥 Q：缓存击穿的互斥锁解决方案具体怎么实现？**

```
public String getData(String key) {
String value = redis.get(key);
if (value != null) return value;  // 缓存命中直接返回
```

```
// 缓存不命中，尝试加锁
String lockKey = "lock:" + key;
if (redis.setnx(lockKey, "1", 10, TimeUnit.SECONDS)) {
// 获取锁的线程去查 DB
value = db.query(key);
redis.set(key, value, 300, TimeUnit.SECONDS);
redis.del(lockKey);
return value;
} else {
// 其他线程等待一会重试
Thread.sleep(50);
return getData(key);  // 递归重试
}
}
```
