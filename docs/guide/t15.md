# 15. 运行时数据区

**一句话定位**：JVM 把内存分成五块——**程序计数器、虚拟机栈、本地方法栈**是线程私有，**堆、方法区（元空间）**是线程共享；此外还有不受 JVM 规范管理的**直接内存**。

## 一、全景图

```
┌───────────────────────── JVM 进程 ─────────────────────────┐
│  线程私有                     线程共享                       │
│  ┌──────────────┐            ┌──────────────────────────┐  │
│  │ 程序计数器 PC │            │ 堆 Heap                   │  │
│  ├──────────────┤            │  ├─ 新生代 Eden/S0/S1     │  │
│  │ 虚拟机栈      │            │  └─ 老年代                │  │
│  │  ├ 栈帧       │            ├──────────────────────────┤  │
│  │  ├ 栈帧       │            │ 方法区（JDK 8+ 元空间）    │  │
│  ├──────────────┤            │  类元数据 / 运行时常量池    │  │
│  │ 本地方法栈    │            └──────────────────────────┘  │
│  └──────────────┘                                          │
│  ┌──────────────────────────────────────────────────────┐  │
│  │ 直接内存 Direct Memory（NIO ByteBuffer.allocateDirect）│  │
│  └──────────────────────────────────────────────────────┘  │
└────────────────────────────────────────────────────────────┘
```

## 二、五个区域逐个说

| 区域 | 线程 | 作用 | 会抛什么 |
| --- | --- | --- | --- |
| 程序计数器 | 私有 | 记录当前线程执行到哪条字节码 | 无（唯一不 OOM 的区域） |
| 虚拟机栈 | 私有 | 每个方法一个栈帧：局部变量表、操作数栈、动态链接、返回地址 | `StackOverflowError` / OOM |
| 本地方法栈 | 私有 | 服务 native 方法（HotSpot 与虚拟机栈合并实现） | `StackOverflowError` / OOM |
| 堆 | 共享 | 对象实例、数组 | `OutOfMemoryError: Java heap space` |
| 方法区 | 共享 | 类元数据、运行时常量池、JIT 代码缓存 | `OutOfMemoryError: Metaspace` |

### 程序计数器

::: tip
线程切换回来后靠它恢复执行位置。它是唯一**不会 OOM** 的区域——它只存一个行号，范围确定；执行 native 方法时值为 `undefined`。

:::

### 虚拟机栈

```text
栈帧（Frame）
├── 局部变量表    slot 为单位（32 位），long/double 占两个 slot；实例方法第 0 个 slot 是 this
├── 操作数栈      字节码运算的工作区，最大深度在编译期确定
├── 动态链接      指向运行时常量池中该方法的符号引用
├── 方法返回地址  正常返回/异常退出的下一条指令
└── 附加信息
```

两种异常要分清：

- **StackOverflowError**：栈深度超过 `-Xss` 限制，典型是无限递归；
- **OutOfMemoryError**：栈可以动态扩展，但申请不到内存（HotSpot 的栈固定大小，基本只会在创建线程时触发 `unable to create new native thread`）。

栈帧大小在编译期确定，方法调用时分配，返回时弹出，不需要 GC。

### 堆

对象和数组的分配场所，GC 的主战场。分代是**实现选择**，不是 JVM 规范要求（ZGC 在 JDK 21 之前不分代）。默认参数下：

```
Eden : S0 : S1 = 8 : 1 : 1        -XX:SurvivorRatio=8
新生代 : 老年代 = 1 : 2            -XX:NewRatio=2
```

### 方法区 / 元空间

JDK 8 之前叫永久代（PermGen），在堆内、受 `-XX:MaxPermSize` 限制；JDK 8 起改为 **Metaspace**，使用本地内存。

元空间存的是**类的元数据**：Klass 结构、方法字节码、字段描述、运行时常量池、注解、JIT 编译产物（部分在 CodeCache）。

这里有个高频错误：**JDK 8 的静态变量不在元空间，而在堆里**。`static` 字段跟随 `java.lang.Class` 对象存放在堆中；元空间只放类的元数据。JDK 7 把字符串常量池从永久代移到堆，JDK 8 又把剩下的元数据移出堆，这两次迁移要分清。

::: danger
需要 `-XX:MaxMetaspaceSize` 设上限。不设时默认只受物理内存限制，一旦类加载泄漏（动态生成类、热部署），会把机器内存吃光，表现形式是容器 OOMKilled 而不是 Java 的 OOM。

:::

### 直接内存

`ByteBuffer.allocateDirect()` 分配在堆外，不受 `-Xmx` 限制，受 `-XX:MaxDirectMemorySize` 限制（默认等于 `-Xmx`）。NIO、Netty 大量使用，好处是少一次堆内到堆外的拷贝。

## 三、OOM 场景对照表

| 报错 | 常见原因 | 排查方向 |
| --- | --- | --- |
| `Java heap space` | 对象太多/太大、内存泄漏、`-Xmx` 太小 | dump 堆，MAT 看支配树 |
| `GC overhead limit exceeded` | 98% 时间在 GC 却只回收不到 2% | 同上，通常是内存泄漏 |
| `Metaspace` | 动态生成类过多（CGLIB、Groovy、热部署） | `jcmd GC.class_stats`、检查类加载器泄漏 |
| `Direct buffer memory` | Netty/NIO 直接内存未释放 | `-XX:MaxDirectMemorySize`、检查 `ByteBuf` 泄漏 |
| `unable to create new native thread` | 线程数超过系统限制 | `ulimit -u`、线程池是否无限创建 |
| `Requested array size exceeds VM limit` | 数组长度接近 `Integer.MAX_VALUE` | 检查业务数据量 |

## 四、为什么 JDK 8 用 Metaspace 替换 PermGen

| 维度 | PermGen | Metaspace |
| --- | --- | --- |
| 内存位置 | 堆内（受 `-Xmx` 约束） | 本地内存（不受 `-Xmx` 约束） |
| 上限 | 固定 `-XX:MaxPermSize` | 默认无上限，可设 `-XX:MaxMetaspaceSize` |
| 调优 | 需要预估类元数据大小，估小就 OOM | 按需增长，减少“拍脑袋设参数” |
| 回收 | Full GC 时回收，效率低 | 类卸载时回收，配合 `Class unloading` |
| 字符串常量池 | JDK 7 已移到堆 | 仍在堆（不属于 Meta） |

核心动机：**PermGen 的大小很难预估**。大量使用动态代理、JSP、OSGi 的应用，类数量波动大，固定上限不是 OOM 就是浪费。Metaspace 用本地内存按需分配，把“容量规划”问题变成“监控增长”问题。

## 五、面试连环问

**Q：哪些区域线程私有？**

程序计数器、虚拟机栈、本地方法栈。堆和方法区线程共享。

**Q：程序计数器为什么不会 OOM？**

它只保存当前字节码的行号，是一个固定大小的整数，生命周期随线程，不涉及内存分配。

**Q：栈和堆的区别？**

栈存方法调用和局部变量，线程私有，自动分配释放；堆存对象实例，线程共享，由 GC 管理。栈溢出是 `StackOverflowError`，堆溢出是 `OutOfMemoryError`。

**Q：JDK 8 的静态变量存在哪？**

堆。`static` 字段属于 `Class` 对象，`Class` 对象在堆中；元空间只存类的元数据。这是“方法区存静态变量”这个老说法在 JDK 8 之后的常见误答。

**Q：字符串常量池在哪？**

JDK 7 起在堆中（`StringTable`），不在元空间。`intern()` 把字符串放进这个池。

**Q：元空间会 OOM 吗？**

会。`MaxMetaspaceSize` 设了上限，或者本地内存耗尽时，抛 `OutOfMemoryError: Metaspace`。默认不设上限只是“不容易撞到 Java 层的限制”，容器里仍可能被 OOMKilled。

**Q：直接内存受 `-Xmx` 限制吗？**

不受。受 `-XX:MaxDirectMemorySize` 限制（默认等于 `-Xmx`），并且算在进程的物理内存里。设置堆大小时要给直接内存留余量。
