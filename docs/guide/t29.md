# 29. IoC 与 DI

**一句话定位**：IoC 是“把对象的创建权交给容器”，DI 是“容器把依赖塞进来”；两者是同一件事的**控制反转视角**和**依赖注入视角**。

## 一、IoC 与 DI 的关系

```java
// 自己 new：控制权在业务代码
OrderService service = new OrderService(new OrderDao(new DataSource(...)));

// IoC：容器创建并组装
@Autowired
private OrderService service;
```

| 概念 | 关注点 |
| --- | --- |
| IoC（控制反转） | 对象的**创建和生命周期**由容器管理，而不是调用方 |
| DI（依赖注入） | 容器把**依赖对象**注入到目标对象中 |

IoC 是思想，DI 是实现手段。Spring 的 IoC 容器 = `BeanDefinition` 注册表 + 单例池 + 依赖解析 + 生命周期管理。

## 二、BeanFactory 与 ApplicationContext

| 能力 | BeanFactory | ApplicationContext |
| --- | --- | --- |
| Bean 的创建与管理 | ✅ | ✅ |
| 国际化（MessageSource） | ❌ | ✅ |
| 事件发布（ApplicationEvent） | ❌ | ✅ |
| 资源加载（Resource） | ❌ | ✅ |
| 环境与 Profile | ❌ | ✅ |
| AOP 自动代理 | 需手动注册 | ✅ 自动 |
| Bean 加载时机 | **懒加载**（getBean 时） | **启动时**预实例化单例 |

`ApplicationContext` 继承 `BeanFactory`，是它的增强版。日常开发用的 `ClassPathXmlApplicationContext`、`AnnotationConfigApplicationContext`、`SpringApplication` 都是 ApplicationContext。

## 三、容器启动：refresh() 的十二步

```java
public void refresh() throws BeansException, IllegalStateException {
    prepareRefresh();                          // ① 记录启动时间、初始化环境
    ConfigurableListableBeanFactory beanFactory = obtainFreshBeanFactory();  // ② 创建/获取 BeanFactory
    prepareBeanFactory(beanFactory);           // ③ 注册内置 BeanPostProcessor、类加载器等
    postProcessBeanFactory(beanFactory);       // ④ 子类扩展点
    invokeBeanFactoryPostProcessors(beanFactory);  // ⑤ 执行 BeanFactoryPostProcessor（如解析 @Configuration）
    registerBeanPostProcessors(beanFactory);   // ⑥ 注册 BeanPostProcessor
    initMessageSource();                       // ⑦ 国际化
    initApplicationEventMulticaster();         // ⑧ 事件广播器
    onRefresh();                               // ⑨ 子类扩展（如 Tomcat 启动）
    registerListeners();                       // ⑩ 注册监听器
    finishBeanFactoryInitialization(beanFactory);  // ⑪ 实例化所有非懒加载单例
    finishRefresh();                           // ⑫ 发布 ContextRefreshedEvent
}
```

第 ⑤ 步最关键：`ConfigurationClassPostProcessor` 在这里解析 `@Configuration`、`@ComponentScan`、`@Import`、`@Bean`，把所有 BeanDefinition 注册进容器。第 ⑪ 步才真正创建 Bean。

## 四、Bean 的生命周期

```
① 实例化（构造器）
② 属性填充（populateBean，注入依赖）
③ Aware 回调：BeanNameAware → BeanClassLoaderAware → BeanFactoryAware
④ BeanPostProcessor#postProcessBeforeInitialization
⑤ 初始化：@PostConstruct → InitializingBean#afterPropertiesSet → init-method
⑥ BeanPostProcessor#postProcessAfterInitialization   ← AOP 代理在这里生成
⑦ Bean 就绪，放入单例池
⑧ 容器关闭：@PreDestroy → DisposableBean#destroy → destroy-method
```

几个高频追问：

- **AOP 代理是在第 ⑥ 步生成的**：`AbstractAutoProxyCreator` 实现 `BeanPostProcessor`，在 `postProcessAfterInitialization` 里判断是否需要代理，需要就返回代理对象替换原始对象。
- **`@PostConstruct` 在 `afterPropertiesSet` 之前**：前者由 `CommonAnnotationBeanPostProcessor` 处理，后者是 `InitializingBean` 接口方法。
- **原型 Bean 的销毁方法不会被调用**：容器不管理原型的完整生命周期，`@PreDestroy` 不执行。

## 五、三种注入方式

```java
// ① 构造器注入（推荐）
@Service
public class OrderService {
    private final OrderDao orderDao;
    public OrderService(OrderDao orderDao) { this.orderDao = orderDao; }
}

// ② Setter 注入
@Autowired
public void setOrderDao(OrderDao orderDao) { this.orderDao = orderDao; }

// ③ 字段注入
@Autowired
private OrderDao orderDao;
```

| 维度 | 构造器 | Setter | 字段 |
| --- | --- | --- | --- |
| 不可变 | ✅ `final` | ❌ | ❌ |
| 依赖完整性 | ✅ 创建时必须给全 | ❌ 可能漏注入 | ❌ 可能漏注入 |
| 循环依赖 | ❌ 无法解决（除非 `@Lazy`） | ✅ | ✅ |
| 单元测试 | ✅ 直接 new | ✅ | ❌ 需要反射/容器 |
| 代码可读性 | ✅ 依赖一目了然 | 中 | 差（隐藏依赖） |

Spring 官方推荐**构造器注入**：依赖不可变、不为 null、容易测试、能在编译期发现循环依赖。字段注入只适合快速原型。

## 六、@Autowired 与 @Resource

| 维度 | `@Autowired` | `@Resource` |
| --- | --- | --- |
| 来源 | Spring | JSR-250（`jakarta.annotation`） |
| 匹配方式 | **先 byType**，多个候选再 byName | **先 byName**，找不到再 byType |
| 是否必须 | `required` 默认 true | 默认必须找到 |
| 配合注解 | `@Qualifier` 指定名字 | `name` 属性指定名字 |
| 适用位置 | 构造器、方法、字段、参数 | 字段、Setter |

```java
@Autowired
@Qualifier("orderDaoImpl")
private OrderDao orderDao;

@Resource(name = "orderDaoImpl")
private OrderDao orderDao;
```

## 七、循环依赖与三级缓存

```java
@Service
public class A { @Autowired private B b; }

@Service
public class B { @Autowired private A a; }
```

Spring 用三级缓存解决**单例 + 字段/Setter 注入**的循环依赖：

| 缓存 | 名字 | 存什么 |
| --- | --- | --- |
| 一级 | `singletonObjects` | 完整初始化好的 Bean |
| 二级 | `earlySingletonObjects` | 提前暴露的早期引用（可能已是被 AOP 包装的代理） |
| 三级 | `singletonFactories` | `ObjectFactory`，调用 `getObject()` 生成早期引用 |

创建 A 的过程：

```
① 实例化 A（构造器），得到原始对象
② 把 A 的 ObjectFactory 放入三级缓存
③ 填充属性，发现依赖 B → 去创建 B
④ 实例化 B，填充属性，发现依赖 A
⑤ 从一级缓存找不到 A → 二级缓存找不到 → 三级缓存拿到 ObjectFactory
⑥ 调用 getObject() 得到 A 的早期引用（此时如果需要 AOP，就在这里生成代理）
⑦ 把早期引用放入二级缓存，从三级缓存移除
⑧ B 注入 A 的早期引用，B 完成初始化，放入一级缓存
⑨ 回到 A，注入 B，A 完成初始化，放入一级缓存
```

**为什么需要三级而不是两级**：如果只有二级缓存，那么任何 Bean 在实例化后都必须立刻判断是否需要 AOP 并生成代理，即使根本没有循环依赖——这会让所有 Bean 都提前走一遍代理逻辑，破坏正常生命周期。三级缓存把“是否提前生成代理”延迟到真正发生循环依赖时。

**哪些循环依赖解决不了**：

| 场景 | 原因 |
| --- | --- |
| 构造器注入循环依赖 | 对象还没实例化就要依赖，无法提前暴露 |
| 原型（prototype）循环依赖 | 原型不缓存，无法提前暴露 |
| `@Async` 代理的循环依赖 | 代理在初始化后生成，早期引用拿不到 |

Spring Boot 2.6+ 默认**禁止循环依赖**（`spring.main.allow-circular-references=false`），出现循环依赖直接启动失败——这是有意为之，循环依赖本身是设计问题，应该重构而不是靠三级缓存兜着。

## 八、Bean 的作用域

| 作用域 | 说明 |
| --- | --- |
| singleton | 默认，容器内一个实例 |
| prototype | 每次 getBean 创建新实例，容器不管理销毁 |
| request | 每个 HTTP 请求一个实例（Web） |
| session | 每个会话一个实例（Web） |
| application | 每个 ServletContext 一个实例（Web） |
| websocket | 每个 WebSocket 会话一个实例（Web） |

单例 Bean 注入原型 Bean 时，原型只会被注入一次——需要每次拿新实例时用 `ObjectProvider` 或 `@Lookup`。

## 九、面试连环问

**Q：IoC 和 DI 的区别？**

IoC 是“控制权反转”的思想：对象创建交给容器。DI 是实现 IoC 的手段：容器把依赖注入进来。说“Spring 的 IoC 是通过 DI 实现的”即可。

**Q：BeanFactory 和 ApplicationContext 的区别？**

ApplicationContext 继承 BeanFactory，额外提供国际化、事件、资源加载、环境、自动 AOP 等能力；BeanFactory 懒加载，ApplicationContext 默认启动时实例化单例。

**Q：Bean 的生命周期？**

实例化 → 属性填充 → Aware 回调 → `BeanPostProcessor#before` → 初始化方法（`@PostConstruct` → `afterPropertiesSet` → `init-method`）→ `BeanPostProcessor#after`（AOP 代理）→ 使用 → 销毁（`@PreDestroy` → `destroy` → `destroy-method`）。

**Q：Spring 怎么解决循环依赖？**

三级缓存：一级存完整 Bean，二级存早期引用，三级存 ObjectFactory。创建 A 时提前把工厂放入三级缓存，B 依赖 A 时通过工厂拿到早期引用（必要时在这里生成 AOP 代理），从而打破循环。构造器注入和原型作用域无法解决。

**Q：为什么需要三级缓存，二级不够吗？**

二级缓存能解决普通循环依赖，但无法处理“需要 AOP 的 Bean”。三级缓存的 ObjectFactory 把代理生成延迟到真正发生循环依赖时，避免所有 Bean 都提前生成代理。

**Q：@Autowired 和 @Resource 的区别？**

`@Autowired` 是 Spring 的，先 byType 再 byName，可配 `@Qualifier`；`@Resource` 是 JSR-250 的，先 byName 再 byType，用 `name` 指定。字段注入优先用 `@Resource`（按名字更直观），构造器注入只能用 `@Autowired`。

**Q：为什么推荐构造器注入？**

依赖 final 不可变、创建时强制给全、不依赖容器即可单测、循环依赖在启动时就暴露。字段注入隐藏依赖、无法声明为 final、单测要反射。
