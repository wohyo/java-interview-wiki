# 20. 三大日志

**Q：MySQL InnoDB 的三大日志？分别的职责？**

| 日志 | 所在层 | 内容 | 用途 |
| --- | --- | --- | --- |
| redo log | InnoDB 引擎层 | 物理日志（数据页修改记录） | 崩溃恢复 crash-safe |
| undo log | InnoDB 引擎层 | 逻辑日志（数据修改前的值） | 事务回滚 + MVCC |
| bin log | MySQL Server 层 | 逻辑日志（SQL 原文或行变更） | 主从复制 + 数据恢复 |

**🔥 Q：redo log 的两阶段提交（Two-Phase Commit）？解决了什么问题？**

背景：事务提交时，redo log 和 bin log 都需要写。如果不一致，可能导致主从数据不一致或数据恢复错乱。

两阶段提交流程：

```
1. Prepare 阶段 → redo log 写入并标记为 PREPARE
2. Commit 阶段 → bin log 写入
3. 写入事务 commit 标识 → redo log 标记为 COMMIT
```

解决了什么问题：

如果写 bin log 前宕机 → 恢复时发现 redo log 为 PREPARE，bin log 未写 → 回滚

如果写完 bin log 但标记 COMMIT 前宕机 → 恢复时发现 bin log 已写，redo log 为 PREPARE → 补全 COMMIT

保证 redo log 和 bin log 的一致性

**🔥 Q：redo log 和 bin log 的区别？**

|  | redo log | bin log |
| --- | --- | --- |
| 所属层 | InnoDB 引擎层 | MySQL Server 层 |
| 内容 | 物理日志（第几号数据页、页内偏移量、修改了什么字节） | 逻辑日志（SQL 语句或行数据变更） |
| 写入方式 | 循环写，固定大小（默认 48MB × 每个文件） | 追加写，文件达到上限后滚动（可全量恢复） |
| 用途 | 崩溃恢复（crash-safe） | 主从复制、时间点恢复 |
