# 20. 三大日志

**Q：MySQL 的三大日志分别是什么？各自职责？**

| 日志 | 层级 | 类型 | 记录内容 | 作用 | 写入方式 |
| --- | --- | --- | --- | --- | --- |
| undo log | InnoDB 引擎层 | 逻辑日志 | 修改前的旧值 / 旧版本 | 事务回滚 + MVCC | 写入 undo 表空间，Purge 后空间可复用 |
| redo log | InnoDB 引擎层 | 物理日志 | 数据页的物理修改 | 崩溃恢复（crash-safe） | 循环写，容量固定 |
| binlog | MySQL Server 层 | 逻辑日志 | SQL 原文或行变更 | 主从复制 + 备份恢复 | 追加写，写满切文件 |

记忆口诀：**undo 管后悔，redo 管保命，binlog 管传宗接代。**

先记分层：undo 和 redo 是 InnoDB 引擎自己的日志，binlog 是 Server 层的日志、与存储引擎无关。所以换引擎 binlog 还在，undo / redo 就没了。

## 一、redo log

**Q：为什么需要 redo log？直接改完就刷盘不行吗？**

InnoDB 的修改不是直接写磁盘，而是先改 Buffer Pool 里的数据页，这些被改过但还没落盘的页叫**脏页**，由后台线程异步刷盘。

如果崩溃时脏页还没刷，改动就丢了。redo log 就是为此存在的，它遵循 **WAL（Write-Ahead Logging）**：

1. 先把"哪个数据页被改成了什么"顺序写进 redo log 并落盘；
2. 事务就可以提交，脏页慢慢刷；
3. 崩溃重启时重放 redo log，把还没刷盘的改动补回来。

为什么不让每次修改都直接随机写数据页？两个原因：

- **顺序 IO 远快于随机 IO**：redo 是追加写，刷脏页要在磁盘上随机找多个页；
- **一次事务可能改多个页**：redo 只需一次小的顺序写，就能保证整组修改的原子提交。

**Q：redo log 的物理结构？**

redo 记录的是"表空间号 + 页号 + 页内偏移 + 修改后的字节"，是**物理日志**，不是 SQL。

写入路径是：修改 Buffer Pool 中的数据页 → 生成 redo 记录写入 **log buffer** → 事务提交时按策略刷盘。

文件组织是**循环写**：

```
┌─────────────── redo log 文件组（固定容量）────────────────┐
│  ... 已可覆盖  ... │ checkpoint │── 已写未刷脏 ──│ write pos │
└──────────────────────────────────────────────────────────┘
                      ↑ 可覆盖起点              ↑ 当前写位置
```

- `write pos`：当前写到哪里；
- `checkpoint`：这个位置之前的 redo 对应的脏页都已经刷盘，日志可以被覆盖；
- 两者之间是空闲空间。写满时会推动 checkpoint 强制刷脏页，然后从头覆盖。

容量演变要注意版本：

| 版本 | 配置 | 默认值 |
| --- | --- | --- |
| 8.0.30 之前 | `innodb_log_file_size` × `innodb_log_files_in_group` | 48MB × 2 |
| 8.0.30 起 | `innodb_redo_log_capacity` | 100MB，底层拆成 `#innodb_redo` 目录下的 32 个文件 |

**🔥 Q：innodb_flush_log_at_trx_commit 三个值有什么区别？**

| 值 | 提交时的行为 | 崩溃后果 |
| --- | --- | --- |
| `1`（默认） | 每次提交都 write + fsync | 最安全，不丢已提交事务，但每次提交都有一次磁盘同步 |
| `0` | 提交时不写，后台每秒 write + fsync | 实例崩溃或断电都可能丢最近约 1 秒的事务 |
| `2` | 提交时 write 到操作系统缓存，不 fsync | 数据库进程崩溃不丢（数据已在 OS 缓存），机器断电可能丢约 1 秒 |

`1` 是金融类业务的底线；`2` 在"只允许进程崩溃、不允许断电"的前提下性能更好。

## 二、undo log

**🔥 Q：undo log 记录什么？INSERT / UPDATE / DELETE 有什么区别？**

undo 是**逻辑日志**，记录的不是"页改成什么"，而是"怎么撤销这次修改"。

| 操作 | undo 记录内容 | 回滚时执行 |
| --- | --- | --- |
| INSERT | 只记主键 | 按主键删除该行 |
| UPDATE | 被更新列的旧值 | 反向 UPDATE 回旧值 |
| DELETE | 整行旧数据 | 重新插入整行 |

注意 InnoDB 的 DELETE 实际是**删除标记**（delete mark），行还在页里，只是打上删除位；undo 记录配合标记位完成回滚。

undo 有两个用途：

1. **事务回滚**：`ROLLBACK` 时按 undo 反向执行；
2. **MVCC**：把一行的历史版本串成版本链，快照读沿链回溯。

补充一点：undo 页本身的修改也会写 redo，所以 undo 也受崩溃恢复保护，不会出现"数据页恢复了、undo 没了"的情况。

**🔥 Q：undo log 的物理存储结构？**

undo 不是一个大文件，而是五层嵌套：

```
Undo Tablespace（undo 表空间）
  └── Rollback Segment（回滚段，默认 128 个）
        └── Undo Segment（undo 段，事务专用，最多两个）
              └── Undo Slot（槽位，16KB 页时 1024 个）
                    └── Undo Log Record（具体的 undo 记录）
```

| 层级 | 关键点 |
| --- | --- |
| undo 表空间 | 8.0 默认两个：数据目录下的 `undo_001`、`undo_002`（没有扩展名）。`innodb_undo_tablespaces` 从 8.0.14 起已废弃，固定 2 个；可以用 `CREATE UNDO TABLESPACE` 新建，用户自建的 undo 表空间文件才带 `.ibu` 后缀 |
| 回滚段 | `innodb_rollback_segments` 默认 128。事务开始时绑定一个，之后该事务的 undo 都写进这个回滚段 |
| undo 段 | 事务专用，最多两个：insert undo 段只服务 INSERT，事务提交后即可释放；update undo 段服务 UPDATE/DELETE，必须等 Purge 判断没有 Read View 引用 |
| 槽位 | 16KB 页时 1024 个，用来定位具体的 undo 记录；页大小不同，数量也不同 |
| undo 记录 | 类型（`TRX_UNDO_INSERT_REC` / `TRX_UNDO_UPD_EXIST_REC` / `TRX_UNDO_DEL_MARK_REC`）+ table_id + trx_id + roll_ptr + 旧列值 |

**Q：DB_ROLL_PTR 这 7 个字节存了什么？**

`DB_ROLL_PTR` 是行记录里的隐藏字段，7 字节 = 56 bit，它不是内存地址，而是一个**逻辑地址**，拆开是这样：

| 位 | 字段 | 位数 | 作用 |
| --- | --- | --- | --- |
| bit 55 | `is_insert` | 1 | 1 表示 insert undo，0 表示 update undo |
| bit 54 ~ 48 | `rseg_id` | 7 | 回滚段号，0 ~ 127 |
| bit 47 ~ 16 | `page_no` | 32 | undo 页号 |
| bit 15 ~ 0 | `offset` | 16 | undo 页内偏移 |

所以定位一个旧版本要走"回滚段 → undo 页 → 页内偏移"三级，而不是直接拿一个指针。网上有些资料写成"回滚段号 7 bit + 槽位号 10 bit + 偏移 39 bit"，和 InnoDB 源码的结构对不上。

**🔥 Q：Purge 线程怎么判断一个 undo 版本可以清理？**

事务提交后，undo 段不会立刻删除，而是按提交顺序挂到 **History List**（历史链表）尾部。Purge 线程周期性遍历，判断条件是一句话：

> **可清理条件：`T.TRX_ID < 所有活跃 Read View 的 min_trx_id 的最小值`**

其中"所有活跃 Read View 的 min_trx_id 的最小值"可以理解为全局最老的快照边界。

举例：当前有三个活跃 Read View，`min_trx_id` 分别是 200、250、300，全局最小值就是 200。

| History List 中的事务 | TRX_ID | 判断 | 结果 |
| --- | --- | --- | --- |
| T1 | 100 | 100 < 200 ✅ | 可以清理 |
| T2 | 180 | 180 < 200 ✅ | 可以清理 |
| T3 | 220 | 220 < 200 ❌ | 保留，可能还有快照要读 |

清理动作：从 History List 头部移除 → 释放 undo 段 → undo 记录标记可复用 → 整页空了就释放页 → 整个 undo 表空间空了可以截断（`innodb_undo_log_truncate = ON`，默认开启，单表空间上限由 `innodb_max_undo_log_size` 控制，默认 1G）。

**Q：长事务为什么危险？**

一个长事务的 Read View 长期存活，它的 `min_trx_id` 会一直压低全局最小值，导致它之后的 undo 版本全都不能清理：

```
长事务 X（TRX_ID=150）一直不提交
  → global_min_trx_id = 150
  → 所有 TRX_ID >= 150 的 undo 版本都无法清理
  → History List 越来越长
  → undo 表空间持续膨胀，最终可能写满磁盘
  → 版本链变长，快照读回溯次数增加，查询变慢
```

这比锁等待更隐蔽：锁等待你能看到阻塞，undo 膨胀是慢慢把库拖死。

监控长事务：

```sql
SELECT trx_id, trx_state, trx_started, trx_mysql_thread_id,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS duration_seconds
FROM information_schema.innodb_trx
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
ORDER BY trx_started;
```

治理手段：拆分大事务、批量操作分批提交、阈值告警、必要时 `KILL`、开启 `innodb_undo_log_truncate`。

## 三、binlog

**Q：binlog 是什么？和 redo 有什么本质区别？**

binlog 是 **Server 层**的逻辑日志，记录的是"逻辑上发生了什么"：要么是 SQL 语句，要么是行数据的前后镜像。它追加写、不循环，写满 `max_binlog_size`（默认 1G）就切下一个文件，所以配合全量备份可以恢复到任意时间点。

**🔥 Q：binlog 的三种格式怎么选？**

| 格式 | 记录内容 | 优点 | 缺点 |
| --- | --- | --- | --- |
| `STATEMENT` | SQL 原文 | 日志小，可读性好 | 含 `NOW()`、`UUID()`、`RAND()` 或不确定顺序的语句时，主从可能不一致 |
| `ROW`（5.7 起默认） | 每行变更前后的值 | 精确，不依赖执行环境 | 日志量大，批量更新会膨胀 |
| `MIXED` | 一般不定期用 STATEMENT，遇到不确定语句自动切 ROW | 兼顾体积与安全 | 行为不如 ROW 直观 |

`ROW` 格式下还有一个 `binlog_row_image` 参数（默认 `FULL`，记录整行前后镜像；`MINIMAL` 只记被改的列和主键），能进一步压缩日志。

刷盘由 `sync_binlog` 控制：`1`（8.0 默认）表示每次提交都 fsync，最安全；`0` 交给操作系统，性能好但有丢失风险。

## 四、两阶段提交

**🔥 Q：一条 UPDATE 的完整执行顺序？**

```sql
UPDATE user SET age = 21 WHERE id = 1;   -- 原 age = 20
```

```
① 从 Buffer Pool 找 id=1 的数据页（不在则从磁盘加载）
        ↓
② 生成 undo log：记录旧值 age=20
        ↓
③ 修改 Buffer Pool 中的数据页：age 20 → 21（产生脏页）
        ↓
④ 生成 redo log：记录数据页的物理修改（此时只在 log buffer）
        ↓
════════════ 客户端执行 COMMIT ════════════
        ↓
⑤ Prepare 阶段：redo log 刷盘，标记为 prepare，写入 XID
        ↓
⑥ 写 binlog：binlog 刷盘，末尾写入同一个 XID
        ↓
⑦ Commit 阶段：redo log 标记为 commit
        ↓
⑧ 返回客户端"更新成功"
```

一句话：**undo → 改内存 → redo(prepare) → binlog → redo(commit)**。

**🔥 Q：为什么需要两阶段提交？**

因为 redo 和 binlog 是两套独立日志，必须保证"要么都算提交，要么都不算"。如果只写一个就宕机，会出现主库和从库不一致，或者用备份恢复时数据错乱。

崩溃恢复的判据只有一个：**binlog 里有没有这个 XID**。

| redo 状态 | binlog 有相同 XID？ | 恢复动作 |
| --- | --- | --- |
| commit | — | 已提交，跳过 |
| prepare | ✅ 有 | 补做 commit |
| prepare | ❌ 无 | 回滚事务 |

直观理解：redo 先进入 prepare 并落盘，相当于"我打算提交"；binlog 写成功，相当于"提交被公证了"；最后 redo 标记 commit。崩溃时以 binlog 是否落盘作为最终裁判，所以主库和从库永远能对上。

补充：为了减少 fsync 次数，MySQL 会把多个事务的 redo 刷盘和 binlog 刷盘合并，这就是**组提交（group commit）**。

**🔥 Q：redo log 和 binlog 的区别？**

| 维度 | redo log | binlog |
| --- | --- | --- |
| 所属层 | InnoDB 引擎层 | MySQL Server 层 |
| 日志类型 | 物理日志（页号 + 页内偏移 + 修改的字节） | 逻辑日志（SQL 或行变更） |
| 写入方式 | 循环写，容量固定，写满覆盖 | 追加写，写满切文件，不覆盖 |
| 用途 | 崩溃恢复（crash-safe） | 主从复制、时间点恢复 |
| 事务标识 | 事务提交时写 commit 标记 | 事务末尾写 XID |

四个维度记牢就够了：**分层、类型、写入方式、用途**。

**Q：能不能只用 binlog 做崩溃恢复，不要 redo？**

不行。binlog 是 Server 层的逻辑日志，以事务为单位，无法描述"某个数据页的哪几个字节被改了"；InnoDB 崩溃恢复需要的是页级物理重放，还要配合 LSN / checkpoint 判断哪些页已经刷过、哪些需要重做。两者的粒度和职责都不同，缺一不可。
