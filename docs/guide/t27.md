# 27. 分布式事务

**一句话定位**：本地事务靠数据库的 ACID，跨服务后没有统一的“数据库”，只能在**强一致（2PC/TCC/Seata AT）**和**最终一致（消息、Saga）**之间做选择。

## 一、为什么本地事务不够

```java
@Transactional
public void createOrder() {
    orderDao.insert(order);        // 数据库 A
    stockService.deduct(itemId);   // 服务 B，另一个数据库
    accountService.pay(userId);    // 服务 C，又一个数据库
}
```

`@Transactional` 只能管住当前数据源。B 扣库存成功、C 扣款失败时，A 的回滚管不到 B。要么引入分布式事务，要么靠业务补偿。

## 二、理论基础：CAP 与 BASE

| 理论 | 内容 | 对分布式事务的影响 |
| --- | --- | --- |
| CAP | 分区发生时，一致性 C 和可用性 A 只能选一个 | 强一致方案在分区时会阻塞或降级 |
| BASE | Basically Available、Soft state、Eventually consistent | 最终一致方案的指导思想 |

绝大多数互联网业务选择 **BASE**：允许中间状态，保证最终一致，用补偿/重试/对账兜底。

## 三、2PC（两阶段提交）

```
        协调者（TM）
       ┌────┼────┐
       ▼    ▼    ▼
    参与者A 参与者B 参与者C

阶段一 Prepare：协调者问“能提交吗？”
  参与者：执行本地事务（不提交）→ 锁住资源 → 回复 Yes/No

阶段二 Commit/Rollback：
  全部 Yes → 协调者发 Commit → 各参与者提交
  任一 No 或超时 → 协调者发 Rollback → 各参与者回滚
```

| 优点 | 缺点 |
| --- | --- |
| 强一致，实现相对简单 | **同步阻塞**：Prepare 后资源一直被锁 |
| 数据库层支持（XA） | **协调者单点**：TM 挂了参与者一直锁着 |
| | **数据不一致**：Commit 阶段部分参与者没收到指令 |
| | 性能差，不适合高并发 |

3PC 在 Prepare 和 Commit 之间加了 CanCommit，并引入超时，缓解阻塞，但仍不能完全解决分区问题，实际使用很少。

## 四、TCC（Try-Confirm-Cancel）

TCC 是**业务层面的 2PC**：每个服务实现三个方法。

```java
public interface StockTccService {
    boolean tryDeduct(String orderId, String itemId, int count);   // 预留资源：冻结库存
    boolean confirm(String orderId);                               // 确认：扣减冻结库存
    boolean cancel(String orderId);                                // 取消：释放冻结库存
}
```

```
Try 阶段：各服务预留资源（冻结库存、冻结余额），不真正扣减
Confirm：全部 Try 成功 → 各服务确认，真正扣减
Cancel：任一 Try 失败 → 各服务释放预留资源
```

| 优点 | 缺点 |
| --- | --- |
| 不依赖数据库锁，性能好 | **业务侵入大**，每个服务写三个方法 |
| 资源预留，隔离性好 | 要处理**空回滚**、**悬挂**、**幂等** |
| 可自定义补偿逻辑 | Confirm/Cancel 失败要重试，需保证幂等 |

TCC 的三个经典问题：

| 问题 | 场景 | 解决 |
| --- | --- | --- |
| 空回滚 | Try 没执行（网络问题），Cancel 先到了 | Cancel 判断“有没有对应的 Try 记录”，没有就空回滚 |
| 悬挂 | Cancel 先执行，Try 后到，资源被冻结但没人释放 | Try 前检查是否已 Cancel，已取消则拒绝执行 |
| 幂等 | Confirm/Cancel 被重试多次 | 用事务 ID 去重，或状态机只允许一次状态流转 |

## 五、本地消息表（最终一致）

最常用、落地最简单的方案：

```
业务库（同一个本地事务）
├── 扣款记录
└── 消息表（status = 待发送）

① 本地事务：业务操作 + 插入消息，原子提交
② 定时任务扫描消息表，发送 MQ
③ 发送成功 → 更新消息状态为已发送
④ 消费方消费，幂等处理
⑤ 失败重试；长期失败进死信/人工处理
```

优点：不依赖 MQ 的事务特性，任何 MQ 都能用；本地事务保证“业务 + 消息”原子。
缺点：消息表和业务表耦合，需要定时任务，实时性略差。

## 六、事务消息（RocketMQ）

RocketMQ 把“本地事务 + 消息发送”做成了两阶段：

```
① Producer 发送半消息（half message）到 Broker，此时消费者不可见
② Broker 确认收到，返回成功
③ Producer 执行本地事务
④ Producer 根据本地事务结果，向 Broker 发送 Commit 或 Rollback
⑤ Broker 收到 Commit → 消息对消费者可见；Rollback → 删除半消息
⑥ 如果 Broker 长时间没收到第 ④ 步，回查 Producer 的本地事务状态
```

关键在**事务回查**：Producer 要实现 `checkLocalTransaction`，Broker 定期回查，防止第 ④ 步丢失导致消息状态不明。

## 七、Saga

把一个长事务拆成若干本地事务，每个都有对应的补偿操作：

```
T1 → T2 → T3 → T4
失败时反向补偿：C3 → C2 → C1
```

| 优点 | 缺点 |
| --- | --- |
| 长流程、跨多个服务友好 | **没有隔离性**，中间状态对外可见 |
| 每个服务只做本地事务 | 补偿逻辑要考虑幂等和重试 |
| 适合业务流程长的场景 | 补偿不一定能完全还原（如已发货） |

Saga 分**编排式**（一个协调器决定下一步）和**协同式**（各服务通过事件互相触发）。

## 八、Seata AT

Seata AT 对业务**零侵入**，靠代理数据源自动记录 undo_log：

```
① 开启全局事务，向 TC 注册，拿到 XID
② 执行业务 SQL 前，拦截并记录 before image
③ 执行业务 SQL，记录 after image，一起写入 undo_log
④ 提交前向 TC 注册分支事务，申请全局锁
⑤ 全部成功 → TC 通知提交 → 异步删除 undo_log
⑥ 任一失败 → TC 通知回滚 → 用 undo_log 反向生成 SQL 回滚
```

AT 的隔离级别是**读未提交**（默认）：全局锁只锁住被修改的行，其他事务能读到中间状态。需要读已提交时用 `@GlobalLock` 或 `SELECT ... FOR UPDATE`。

适用：业务简单、不想改代码、能接受最终一致。复杂业务（比如涉及外部接口）仍要 TCC/Saga。

## 九、方案选型

| 方案 | 一致性 | 性能 | 侵入性 | 适用 |
| --- | --- | --- | --- | --- |
| 2PC/XA | 强一致 | 低 | 低（数据库支持） | 内部短事务、低并发 |
| TCC | 强一致（业务层） | 高 | 高 | 资金、库存等核心链路 |
| 本地消息表 | 最终一致 | 高 | 中 | 大多数业务解耦 |
| 事务消息 | 最终一致 | 高 | 中（依赖 RocketMQ） | 已有 RocketMQ 的团队 |
| Saga | 最终一致 | 高 | 中 | 长流程、多服务编排 |
| Seata AT | 最终一致 | 中 | 低 | 快速接入、业务简单 |

选型口诀：**核心资金链路用 TCC，普通业务用消息最终一致，长流程用 Saga，快速接入用 Seata AT**。

## 十、面试连环问

**Q：为什么需要分布式事务？**

本地事务只能保证单个数据库的 ACID。跨服务、跨库后，各服务的提交/回滚无法协调，需要额外的协议或补偿机制。

**Q：2PC 的缺点？**

同步阻塞（Prepare 后一直锁资源）、协调者单点、Commit 阶段网络问题导致部分提交部分回滚、性能差。

**Q：TCC 和 2PC 的区别？**

2PC 是资源层（数据库 XA）的协议，锁的是数据库资源；TCC 是业务层的两阶段，锁的是业务资源（冻结库存/余额），粒度更细、性能更好，但要自己实现三个方法并处理空回滚、悬挂、幂等。

**Q：本地消息表怎么保证不丢消息？**

业务操作和消息插入在**同一个本地事务**里，业务成功则消息一定入库；定时任务扫描未发送的消息并重试，消费方幂等，最终一致。

**Q：RocketMQ 事务消息的回查是做什么的？**

Producer 执行完本地事务后要发 Commit/Rollback，如果这一步失败或超时，Broker 不知道消息该不该投递，于是回查 Producer 的本地事务状态，决定提交还是丢弃。

**Q：Seata AT 的隔离级别？**

默认读未提交。全局锁只锁被修改的行，其他事务可能读到未提交的中间状态；需要更高隔离时用 `@GlobalLock` 或 `for update`。

**Q：最终一致怎么保证数据不丢？**

三个层次：① 本地事务保证业务和消息原子；② 消息中间件保证投递（重试、持久化）；③ 消费方幂等 + 对账兜底。任何一层都可能出问题，所以还要有定时对账。
