# 2. == 与 equals()、hashCode()

**一句话定位**：`==` 比的是**值**（基本类型）或**引用地址**（对象），`equals()` 是方法、默认等同 `==`；`hashCode()` 是散列集合的“桶号”，三者必须配套使用。

## 一、`==` 到底比什么

| 操作数类型 | `==` 的含义 |
| --- | --- |
| 两个基本类型 | 比较数值（会做二元数值提升，`1 == 1.0` 为 true） |
| 两个引用 | 比较是否指向同一个对象（地址） |
| 引用与基本类型 | 编译错误（除包装类型会自动拆箱） |

```java
int a = 1000, b = 1000;
System.out.println(a == b);                 // true，基本类型比数值

Integer c = 1000, d = 1000;
System.out.println(c == d);                 // false，两个不同的堆对象
System.out.println(c.equals(d));            // true

Integer e = 100, f = 100;
System.out.println(e == f);                 // true，命中 IntegerCache
```

## 二、为什么 `Integer` 的 `==` 有时是 true

`Integer.valueOf(int)` 对 **-128 ~ 127** 做了缓存（`IntegerCache`，上界可用 `-XX:AutoBoxCacheMax` 调大）：

```java
public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];
    return new Integer(i);
}
```

自动装箱走的就是 `valueOf`，所以小整数会复用同一个对象。这条规则只保证 **-128~127 必须缓存**，超出范围的行为依赖实现，不能作为业务判断依据。

同理：`Long`、`Short`、`Byte`、`Character` 都有缓存；`Float`、`Double` **没有**（因为范围内取值无限，缓存没意义）。

## 三、`String` 的三种相等

```java
String s1 = "abc";              // 字符串常量池
String s2 = "abc";              // 复用池中对象
String s3 = new String("abc");  // 强制在堆上新造一个
String s4 = s3.intern();        // 返回池中引用

s1 == s2        // true
s1 == s3        // false
s1 == s4        // true
s1.equals(s3)   // true
```

编译器会把字面量拼接（`"a" + "b"`）在编译期折叠成 `"ab"`；但只要有一个操作数是变量，拼接就发生在运行期，结果在堆上。

## 四、equals 的契约

`Object.equals` 的实现就是 `this == obj`。重写必须满足五条：

| 性质 | 要求 |
| --- | --- |
| 自反性 | `x.equals(x)` 为 true |
| 对称性 | `x.equals(y)` 与 `y.equals(x)` 一致 |
| 传递性 | `x=y`、`y=z` 则 `x=z` |
| 一致性 | 对象未变时，多次调用结果不变 |
| 非空性 | `x.equals(null)` 为 false |

对称性最容易踩：`new Date().equals(new Timestamp(...))` 这类跨类型比较，一边用父类实现、一边用子类实现，就可能出现 `a.equals(b)` 为 true 而 `b.equals(a)` 为 false。

标准写法（推荐 IDE 生成 / `Objects.equals`）：

```java
@Override
public boolean equals(Object o) {
    if (this == o) return true;
    if (o == null || getClass() != o.getClass()) return false;
    Student that = (Student) o;
    return id == that.id && Objects.equals(name, that.name);
}

@Override
public int hashCode() {
    return Objects.hash(id, name);
}
```

用 `getClass() != o.getClass()` 而不是 `instanceof`：前者保证对称性（子类不会和父类相等），后者在继承场景下容易破坏对称性。如果确实需要“父类与子类可相等”，就得放弃 `instanceof` 之外的一致性要求，通常不值得。

## 五、为什么重写 equals 必须重写 hashCode

`Object.hashCode` 的契约只有两条：

1. 同一个对象在未修改时，多次调用返回同一个值；
2. **`equals` 相等的两个对象，`hashCode` 必须相等**（反过来不要求）。

HashMap 的查找是两段式：先 `hash(key)` 定位桶，再在桶内用 `equals` 比较。如果只重写 `equals`，两个“相等”的对象会落到不同的桶：

```java
Map<Student, String> map = new HashMap<>();
map.put(new Student(1, "张三"), "A班");

Student key = new Student(1, "张三");
System.out.println(key.equals(map.keySet().iterator().next()));  // true
System.out.println(map.get(key));                                // null
```

`get` 用的是默认 `Object.hashCode`（与地址相关），算出的桶和 put 时不同，连桶都进不去，自然找不到。这就是“对象放进 HashSet 后改字段就查不到”的根源——`hashCode` 变了，桶变了。

## 六、hashCode 的实现建议

| 做法 | 说明 |
| --- | --- |
| `Objects.hash(...)` | 简洁，但每次调用都新建 `Object[]` 并装箱，热点路径有开销 |
| IDE 生成 | 用 31 作为乘子，`31 * h + field`，31 可被 JIT 优化为 `(h<<5)-h` |
| `Objects.hashCode(field)` | 单字段时用它，避免数组开销 |
| 不要用可变字段 | 作为 key 的字段改了，桶就变了，等效于“丢对象” |

为什么是 31：奇素数，乘 31 的结果在溢出时信息保留较好；且 `31 * i == (i << 5) - i`，早期 JVM 能自动优化成移位减法。

## 七、`equals` 和 `compareTo` 要保持一致

`TreeMap`/`TreeSet` 用的是 `compareTo`，`HashMap`/`HashSet` 用的是 `hashCode + equals`。如果 `compareTo` 返回 0 但 `equals` 为 false，同一个对象在 `TreeSet` 里会被当成重复元素丢掉；反过来，两者不一致会让“有序集合”和“散列集合”的去重行为不同。`BigDecimal` 就是典型：`1.0` 与 `1.00` 的 `equals` 为 false（scale 不同），但 `compareTo` 为 0。

## 八、面试连环问

**Q：`==` 和 `equals` 的区别？**

`==` 对基本类型比数值、对引用比地址；`equals` 是方法，`Object` 的默认实现就是地址比较，`String`、包装类、集合等重写成了内容比较。“`==` 比较地址”这句话只对引用类型成立。

**Q：两个对象 `hashCode` 相同，`equals` 一定为 true 吗？**

不一定。哈希碰撞是允许的，HashMap 会在桶内用 `equals` 二次确认。反过来说，`equals` 相等则 `hashCode` 必须相等，这是契约。

**Q：`String` 为什么适合做 HashMap 的 key？**

不可变（hash 可以缓存到 `hash` 字段，只算一次）、`equals`/`hashCode` 已正确实现、常量池复用率高。自定义对象做 key 时，只要保证作为 key 的字段不可变，同样可以。

**Q：重写 `equals` 用 `getClass` 还是 `instanceof`？**

默认用 `getClass`，保证对称性和“只有同类型才相等”。用 `instanceof` 会引入继承下的对称性风险，除非框架有特殊语义（如 Hibernate 代理对象需要 `instanceof` 才能匹配）。

**Q：为什么 `Objects.hash` 在性能敏感场景不推荐？**

它内部是 `Arrays.hashCode(Object[])`，每次调用都要新建数组并把基本类型装箱，热点路径上会产生大量短命对象，增加 GC 压力。手写或用 Lombok 的 `@EqualsAndHashCode` 更可控。
