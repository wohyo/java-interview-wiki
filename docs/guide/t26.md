# 26. 分布式锁

**Q：基于 Redis 的分布式锁如何实现？**

```
// 加锁
Boolean locked = redisTemplate.opsForValue().setIfAbsent("lock:order:123", uuid, 30, TimeUnit.SECONDS);
// 业务处理...
// 释放（用 Lua 保证原子性）
String lua = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class),List.of("lock:order:123"), uuid);
```

**🔥 Q：分布式锁需要考虑哪些问题？**

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 锁超时 | 业务执行时间 > 锁的 TTL，锁自动释放 | Redisson 看门狗（Watch Dog）：后台线程每隔⅓ TTL 续期一次 |
| 锁误删 | 线程 A 的锁超时释放，线程 B加锁，A 恢复后删了 B 的锁 | value 用 UUID 标识，只用 Lua 脚本校验后删除 |
| 主从不一致 | Redis 主节点挂了，从节点还没同步锁数据 | RedLock：向多个节点加锁，半数以上成功才算加锁成功（有争议，复杂场景建议 ZK） |
| 可重入 | 同一线程再次获取同一锁 | ReentrantLock 实现思路：线程标识 + 重入计数 |
| 性能 | 高频加锁/释放 | 考虑分段锁（如 Redis 集群） |

锁超时：业务还没跑完，锁的 TTL 先到期被自动释放，别的线程就进来了，互斥直接失效。解决是 Redisson 的看门狗（Watch Dog）——后台线程每隔 ⅓ TTL 给锁续期，直到业务执行完。

锁误删：线程 A 的锁超时被释放，线程 B 抢到同一把锁，A 执行完回来无条件 del，删掉的其实是 B 的锁。解决是加锁时把 value 写成自己的唯一标识（UUID），释放时先用 Lua 脚本比对 value 再删，比对和删除必须在一次原子操作里完成。

主从不一致：客户端在 master 上加锁成功，master 随即挂掉，而锁数据还没同步到 replica，新主上没有这把锁，别人又能加一次。解决是 RedLock——向多个独立节点分别加锁，半数以上成功才算成功。这套方案本身有争议（时钟跳跃、长 GC 停顿），对正确性要求高的场景建议直接用 ZK。

可重入：同一线程重复获取同一把锁，不能自己把自己挡住。Redis 的实现思路是"线程标识 + 重入计数"，Redisson 用 hash 结构存 线程标识→计数，加锁 +1、释放 -1、归零删 key。

性能：高频加锁释放时单个 key 会成为瓶颈，可以按业务维度分段（比如按订单号、用户 ID 拆 key）来降低锁粒度。

**🔥 Q：Redis 分布式锁 vs ZK 分布式锁的对比？**

|  | Redis | Zookeeper |
| --- | --- | --- |
| 原理 | SETNX + 过期时间 | 临时顺序节点 + watch |
| 性能 | 高（纯内存） | 较低（ZK 写入需过半确认） |
| 锁超时问题 | 有（需看门狗续期） | 无（临时节点绑定 session，断开即释放） |
| 一致性模型 | AP 模型（最终一致） | CP 模型（强一致） |
| 适用 | 对性能要求高，可接受短时间不一致 | 对一致性要求极高（如分布式调度、配置中心） |

原理：Redis 靠 SETNX + 过期时间，锁就是一个 key；ZK 靠临时顺序节点 + watch，创建最小序号节点的客户端拿到锁，其余只监听自己前一个节点，避免羊群效应。

性能：Redis 高，纯内存操作；ZK 较低，每次写入都要过半节点确认。

锁超时：Redis 有这个问题，必须自己续期；ZK 天然没有——临时节点绑定 session，客户端断开或 session 超时节点自动删除，锁随之释放。

一致性：Redis 是 AP 模型，主从异步复制，故障切换时可能丢锁；ZK 是 CP 模型，过半确认才返回成功，锁的强一致有保证。

适用：追求吞吐、能容忍极短时间不一致用 Redis；对正确性要求极高（分布式调度、选主、配置中心）用 ZK。
