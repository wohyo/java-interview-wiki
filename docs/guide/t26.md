# 26. 分布式锁

**Q：基于 Redis 的分布式锁如何实现？**

```
// 加锁
Boolean locked = redisTemplate.opsForValue().setIfAbsent("lock:order:123", uuid, 30, TimeUnit.SECONDS);
// 业务处理...
// 释放（用 Lua 保证原子性）
String lua = "if redis.call('get', KEYS[1]) == ARGV[1] then return redis.call('del', KEYS[1]) else return 0 end";
redisTemplate.execute(new DefaultRedisScript<>(lua, Long.class),List.of("lock:order:123"), uuid);
```

**🔥 Q：分布式锁需要考虑哪些问题？**

| 问题 | 原因 | 解决 |
| --- | --- | --- |
| 锁超时 | 业务执行时间 > 锁的 TTL，锁自动释放 | Redisson 看门狗（Watch Dog）：后台线程每隔⅓ TTL 续期一次 |
| 锁误删 | 线程 A 的锁超时释放，线程 B加锁，A 恢复后删了 B 的锁 | value 用 UUID 标识，只用 Lua 脚本校验后删除 |
| 主从不一致 | Redis 主节点挂了，从节点还没同步锁数据 | RedLock：向多个节点加锁，半数以上成功才算加锁成功（有争议，复杂场景建议 ZK） |
| 可重入 | 同一线程再次获取同一锁 | ReentrantLock 实现思路：线程标识 + 重入计数 |
| 性能 | 高频加锁/释放 | 考虑分段锁（如 Redis 集群） |

**🔥 Q：Redis 分布式锁 vs ZK 分布式锁的对比？**

|  | Redis | Zookeeper |
| --- | --- | --- |
| 原理 | SETNX + 过期时间 | 临时顺序节点 + watch |
| 性能 | 高（纯内存） | 较低（ZK 写入需过半确认） |
| 锁超时问题 | 有（需看门狗续期） | 无（临时节点绑定 session，断开即释放） |
| 一致性强 | AP 模型（最终一致） | CP 模型（强一致） |
| 适用 | 对性能要求高，可接受短时间不一致 | 对一致性要求极高（如分布式调度、配置中心） |
