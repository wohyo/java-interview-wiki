# 1. String、StringBuilder、StringBuffer

**Q：三者的区别？**

都是字符串容器，真正的差别只有两点：能不能改，改的时候安不安全。

String 不可变。内部数组是 `private final`，又不暴露任何修改方法，所以 concat、replace、substring 全都返回新对象。好处是不可变天然线程安全、可以做常量池复用和 hash 缓存；代价是拼接时不断产生新对象、旧对象等 GC，量大时性能最差。用在少量字符串和常量上。

StringBuilder 可变。追加时直接在内部数组上写，不产生新对象，所以单线程大量拼接性能最高。但它没有任何同步措施，多个线程共享同一个实例并发 append，会丢字符、读到中间状态，甚至数组越界抛异常。

StringBuffer 和 StringBuilder 的实现完全一样，唯一区别是每个修改方法都加了 `synchronized`。多线程共享同一个对象时安全，代价是加锁开销，性能比 StringBuilder 略低。

一句话选择：常量用 String，单线程拼接用 StringBuilder，只有多线程共享同一个字符串对象时才用 StringBuffer。JDK 5 之后 StringBuffer 的生存空间很小——拼接一般发生在方法内部，局部变量不存在共享，加锁纯属浪费。

**⚡ Q：String 的不可变性是如何保证的？涉及哪几个层面？**

三个层面：

1. 类被 final 修饰 — 不可被继承，防止子类破坏不可变行为

2. 存储字段被 private final 修饰，且不暴露修改方法

Java 8 及之前：`private final char value[]`

Java 9 及之后：`private final byte[] value` （紧凑字符串）

没有提供 setValue() / 修改内部数组的方法

3. 所有"修改"操作都返回新对象

`concat()` 、`substring()` 、`replace()` 、`toUpperCase()` 都通过 `new String()` 返回新实例，原对象不变

**🔥 Q：Java 9 引入的紧凑字符串（Compact Strings）是什么？为什么这么改？**

背景：Java 8 中 String 用 `char[]` 存储，每个 char 占 2 字节（UTF-16）。但大多数 Latin-1 字符（如英文、数字）只需 1 字节，造成 50% 空间浪费

Java 9 改动：`char[]` → `byte[]` ，引入 `coder` 字段标识编码方式

```
private final byte[] value;
private final byte coder;  // 0 = LATIN1 (1字节), 1 = UTF16 (2字节)
```

效果：纯 Latin-1 字符串内存占用降 50%，GC 压力减小；操作字符串时需判断 coder 并做适配

**🔥 Q：new String("abc") 创建了几个对象？**

1 个或 2 个

若常量池中已有 `"abc"` → 只创建 1 个堆对象（池中已存在，不再创建）

若常量池中没有 `"abc"` → 先创建池中的字面量对象，再 new 一个堆对象，共 2 个

**🔥 Q：intern() 方法的作用和使用注意事项？**

作用：将字符串加入运行时常量池（JDK 7+ 在堆的字符串常量池），返回池中的引用

原理：`"abc".intern()` → 池中已有则返回池中引用，否则将当前对象引用存入池中（JDK 7+ 存引用，不再 copy 对象）

用途：字符串去重，减少内存

```
String s1 = new String("a") + new String("b");  // 堆中 "ab"
String s2 = s1.intern();                         // 池中存入 s1 引用
String s3 = "ab";                                // 直接取池中引用 == s1
```

风险：大量调用 intern() 会导致方法区/元空间膨胀，频繁 Full GC，甚至 OOM: PermGen

替代：JDK 8u20+ 的 G1 GC 提供了 `-XX:+UseStringDeduplication` ，自动去重
