# 24. Redis 跳表

**一句话定位**：跳表是**多层有序链表**，用“随机层数 + 上层快速通道”把查找从 O(n) 降到期望 O(log n)；Redis 用它实现 ZSET 的有序部分。

## 一、ZSET 的两种编码

| 条件 | 编码 | 结构 |
| --- | --- | --- |
| 元素数 ≤ 128 **且** 每个元素长度 ≤ 64 字节 | `listpack`（Redis 7 之前是 `ziplist`） | 紧凑的连续内存，省空间 |
| 超过任一阈值 | `skiplist` + `dict` | 跳表负责按 score 排序，字典负责按 member 查 score |

```bash
# 查看编码
OBJECT ENCODING myzset          # listpack / skiplist
# 阈值可调
zset-max-listpack-entries 128
zset-max-listpack-value 64
```

为什么同时用跳表和字典：

| 操作 | 用谁 | 复杂度 |
| --- | --- | --- |
| `ZSCORE key member` | dict | O(1) |
| `ZRANGE key 0 9` | skiplist | O(log n + k) |
| `ZRANGEBYSCORE key 10 20` | skiplist | O(log n + k) |
| `ZRANK key member` | skiplist（span） | O(log n) |

只用跳表的话，按 member 查 score 需要 O(log n)；只用字典的话，范围查询无法有序。两个结构共享同一份 member/score 数据，内存换性能。

## 二、跳表的结构

```text
level 3:  head ──────────────────────────────→ 30 ─→ NULL
level 2:  head ──────────→ 10 ───────────────→ 30 ─→ NULL
level 1:  head ──→ 5 ────→ 10 ────→ 20 ──────→ 30 ─→ NULL
level 0:  head ──→ 5 ──→ 8 ─→ 10 ─→ 15 ─→ 20 ─→ 25 ─→ 30 ─→ NULL
                  ↑
              底层是全量有序链表，上层是“快速通道”
```

每个节点：

```c
typedef struct zskiplistNode {
    sds ele;                        // member
    double score;                   // 分值
    struct zskiplistNode *backward; // 后退指针，支持 ZREVRANGE
    struct zskiplistLevel {
        struct zskiplistNode *forward;  // 前进指针
        unsigned long span;             // 到下一个节点的跨度（用于算 rank）
    } level[];                          // 柔性数组，层数 1~32
} zskiplistNode;

typedef struct zskiplist {
    struct zskiplistNode *header, *tail;
    unsigned long length;
    int level;                          // 当前最大层数
} zskiplist;
```

两个关键设计：

1. **span（跨度）**：前进指针跨过了多少个底层节点。查找时把路径上的 span 累加，就得到排名 `ZRANK`，不需要额外遍历。
2. **backward（后退指针）**：每个节点只有一个后退指针（只指向底层前一个节点），支持 `ZREVRANGE` 从尾往前遍历。

## 三、查找过程

查找 `score = 20`：

```text
从 header 的最高层 level 3 开始：
  level 3: 下一个是 30 > 20 → 下降
  level 2: 下一个是 10 ≤ 20 → 前进到 10
  level 2: 下一个是 30 > 20 → 下降
  level 1: 下一个是 20 = 20 → 命中
```

规则：**能前进就前进，不能前进就下降**。每一层大约跳过一半（或 1/4）的节点，所以期望查找长度是 O(log n)。

插入时，先找到每层的前驱节点，再随机生成新节点的层数，逐层插入并更新 span。删除同理，逐层摘链并更新 span。

## 四、层数是随机的

```c
int zslRandomLevel(void) {
    int level = 1;
    while ((random() & 0xFFFF) < (ZSKIPLIST_P * 0xFFFF))   // ZSKIPLIST_P = 0.25
        level += 1;
    return (level < ZSKIPLIST_MAXLEVEL) ? level : ZSKIPLIST_MAXLEVEL;  // 最大 32
}
```

- 每升一层的概率是 **1/4**，所以第 k 层的节点数期望是 n/4^k；
- 最大 32 层，按 1/4 的概率，32 层需要 4^32 ≈ 1.8×10^19 个节点，实际永远达不到，只是防御性上限；
- 平均层数约 1.33，额外空间开销可控。

随机层数省掉了平衡树的旋转/变色，插入删除不需要重新平衡，代码简单得多。

## 五、为什么 Redis 用跳表而不是平衡树

| 维度 | 跳表 | 红黑树 / AVL |
| --- | --- | --- |
| 范围查询 | 底层链表，定位起点后顺序遍历 | 需要中序遍历，或维护额外线索 |
| 实现复杂度 | ~200 行，插入删除只改指针 | 旋转、变色、平衡因子，边界情况多 |
| 并发/无锁 | 天然适合（局部修改） | 旋转影响范围大，难做无锁 |
| 内存 | 平均 1.33 个指针/节点 + span | 每个节点固定左右指针 + 颜色 |
| 最坏复杂度 | 概率性 O(log n)（随机层数） | 严格 O(log n) |

Redis 是单线程的，并发不是主要理由；真正的理由是**范围查询**和**实现简单**。ZSET 的核心操作就是 `ZRANGEBYSCORE`、`ZRANGE`，跳表定位到起点后顺着 level 0 链表走即可，平衡树则要不断做中序后继。

### 为什么不用 B+ 树

B+ 树为磁盘设计，节点大、层数少，适合减少磁盘 IO。Redis 是纯内存，节点访问没有 IO 成本，跳表的多层指针更简单；B+ 树的页分裂/合并对内存结构来说是额外复杂度。

## 六、复杂度汇总

| 操作 | 平均 | 最坏 |
| --- | --- | --- |
| `ZADD` | O(log n) | O(n)（层数极端不利时，概率极低） |
| `ZSCORE` | O(1)（走 dict） | O(1) |
| `ZRANK` | O(log n) | O(n) |
| `ZRANGE start stop` | O(log n + k) | O(n) |
| `ZRANGEBYSCORE` | O(log n + k) | O(n) |
| `ZREM` | O(log n) | O(n) |

`k` 是返回的元素个数。

## 七、面试连环问

**Q：ZSET 的底层结构？**

元素少且短时用 listpack（Redis 7 前是 ziplist）；超过阈值用 skiplist + dict。跳表按 score 有序，字典提供 member → score 的 O(1) 查询。

**Q：跳表为什么能做到 O(log n)？**

每层以 1/4 概率向上提升，形成“稀疏索引”。查找时从最高层开始，能前进就前进、不能就下降，每层平均跳过的节点数有限，期望路径长度是 O(log n)。

**Q：跳表的层数是怎么定的？**

插入时随机生成，每升一层概率 1/4，最大 32 层。不是按节点总数计算，也不需要全局重构。

**Q：为什么不用红黑树？**

范围查询更简单（底层链表）、实现更简单（不用旋转）、span 支持 O(log n) 求排名。Redis 单线程，不需要考虑并发优势。

**Q：span 有什么用？**

记录前进指针跨过的底层节点数，查找时累加路径上的 span 就得到排名，`ZRANK` 不用遍历整个链表。

**Q：ZSET 为什么同时用 dict 和 skiplist？**

dict 让 `ZSCORE` 达到 O(1)，skiplist 让范围查询和排名高效。两者共享 member/score，是典型的“空间换时间”。

**Q：跳表的最坏复杂度是多少？**

理论上 O(n)（所有节点都在同一层），但概率极低。随机化的期望复杂度是 O(log n)，实际工程中表现稳定。
