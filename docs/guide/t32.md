# 32. 工厂模式 & 代理模式

**一句话定位**：工厂模式解决“**怎么创建对象**”，代理模式解决“**怎么在不改原对象的前提下增强行为**”；Spring 的核心就是“工厂造 Bean + 代理做 AOP”。

## 一、工厂模式三种形态

### 1. 简单工厂

一个工厂类，根据参数决定创建哪种产品：

```java
public class PayFactory {
    public static PayService create(String type) {
        switch (type) {
            case "alipay": return new AlipayService();
            case "wechat": return new WechatPayService();
            default: throw new IllegalArgumentException("unknown type: " + type);
        }
    }
}
```

缺点：新增产品要改工厂类的 `switch`，违反开闭原则。只适合产品种类很少、稳定的场景。

### 2. 工厂方法

每个产品一个工厂，新增产品只加新工厂，不改旧代码：

```java
public interface PayFactory {
    PayService create();
}

public class AlipayFactory implements PayFactory {
    public PayService create() { return new AlipayService(); }
}

public class WechatFactory implements PayFactory {
    public PayService create() { return new WechatPayService(); }
}
```

符合开闭原则，但类的数量翻倍。

### 3. 抽象工厂

一个工厂创建**一族**相关联的产品：

```java
public interface OrderFactory {
    PayService createPay();
    RefundService createRefund();
    NoticeService createNotice();
}

public class AlipayOrderFactory implements OrderFactory {
    public PayService createPay() { return new AlipayService(); }
    public RefundService createRefund() { return new AlipayRefundService(); }
    public NoticeService createNotice() { return new AlipayNoticeService(); }
}
```

| 模式 | 产品维度 | 新增产品 | 新增产品族 |
| --- | --- | --- | --- |
| 简单工厂 | 单一 | 改工厂 | — |
| 工厂方法 | 单一 | 加工厂类 | — |
| 抽象工厂 | 多个（一族） | 改接口（违反开闭） | 加工厂类 |

抽象工厂的取舍：新增“产品族”（如接入微信支付全家桶）很容易，新增“产品种类”（如加一个对账服务）要改所有工厂接口。

## 二、Spring 里的工厂

| 概念 | 作用 |
| --- | --- |
| `BeanFactory` | IoC 容器顶层接口，`getBean()` 就是工厂方法 |
| `ApplicationContext` | 增强版容器，启动时预实例化单例 |
| `FactoryBean<T>` | “制造 Bean 的 Bean”，`getObject()` 返回真正的对象 |
| `@Bean` 方法 | 在配置类里声明一个 Bean，方法本身就是工厂方法 |
| `BeanFactoryPostProcessor` | 在 Bean 实例化之前修改 BeanDefinition |

`FactoryBean` 的典型用法（MyBatis 的 `MapperFactoryBean`、Spring 的 `ProxyFactoryBean`）：

```java
public class OrderServiceFactoryBean implements FactoryBean<OrderService> {
    @Override
    public OrderService getObject() { return new OrderService(); }

    @Override
    public Class<?> getObjectType() { return OrderService.class; }

    @Override
    public boolean isSingleton() { return true; }
}
```

注意区分：`&orderServiceFactoryBean` 拿到的是 FactoryBean 本身，`orderServiceFactoryBean` 拿到的是 `getObject()` 的产物。

## 三、代理模式

代理在不修改目标对象的前提下，控制对它的访问。三种实现：

### 1. 静态代理

手写一个实现相同接口的类，持有目标对象：

```java
public class OrderServiceProxy implements OrderService {
    private final OrderService target;

    public OrderServiceProxy(OrderService target) { this.target = target; }

    @Override
    public void create(Order order) {
        long start = System.currentTimeMillis();
        target.create(order);
        log.info("create cost {} ms", System.currentTimeMillis() - start);
    }
}
```

缺点：每个接口都要手写一个代理类，方法多了维护成本高。

### 2. JDK 动态代理

```java
OrderService target = new OrderServiceImpl();
OrderService proxy = (OrderService) Proxy.newProxyInstance(
    target.getClass().getClassLoader(),
    target.getClass().getInterfaces(),
    (p, method, args) -> {
        long start = System.currentTimeMillis();
        Object result = method.invoke(target, args);
        log.info("{} cost {} ms", method.getName(), System.currentTimeMillis() - start);
        return result;
    });
```

要求目标类**实现接口**。生成的代理类继承 `Proxy`、实现目标接口，所有方法调用转到 `InvocationHandler`。

### 3. CGLIB 动态代理

```java
Enhancer enhancer = new Enhancer();
enhancer.setSuperclass(OrderServiceImpl.class);
enhancer.setCallback((MethodInterceptor) (obj, method, args, proxy) -> {
    long start = System.currentTimeMillis();
    Object result = proxy.invokeSuper(obj, args);
    log.info("{} cost {} ms", method.getName(), System.currentTimeMillis() - start);
    return result;
});
OrderServiceImpl proxy = (OrderServiceImpl) enhancer.create();
```

通过生成**子类**覆写方法实现代理。要求类和方法**非 final**。

| 维度 | 静态代理 | JDK 动态代理 | CGLIB |
| --- | --- | --- | --- |
| 代理类 | 手写 | 运行时生成 | 运行时生成子类 |
| 前提 | 实现同一接口 | 目标类有接口 | 目标类非 final |
| 方法数 | 每个方法手写 | 统一拦截 | 统一拦截 |
| 性能 | 最高（直接调用） | Java 8+ 接近原生 | 调用略快 |
| Spring | — | 有接口时默认 | 无接口 / Boot 2.x 默认 |

## 四、代理 vs 装饰器 vs 适配器

三个模式结构相似（都是“包一层”），目的不同：

| 模式 | 目的 | 是否改变接口 | 典型例子 |
| --- | --- | --- | --- |
| 代理 | **控制访问**，增强但不改变行为语义 | 不改变 | Spring AOP、RPC 客户端、懒加载 |
| 装饰器 | **动态叠加功能**，可多层嵌套 | 不改变 | `BufferedInputStream(new FileInputStream(...))` |
| 适配器 | **转换接口**，让不兼容的类能协作 | 改变 | `InputStreamReader`（字节流转字符流） |

一句话区分：代理是“替你做事”，装饰器是“给你加功能”，适配器是“换个插头”。

## 五、框架里的实际应用

| 框架 | 用了什么 | 怎么用 |
| --- | --- | --- |
| Spring IoC | 工厂 | `BeanFactory.getBean()` 根据 BeanDefinition 创建对象 |
| Spring AOP | 代理 | JDK/CGLIB 生成代理，织入通知 |
| `@Transactional` | 代理 | 事务拦截器 `TransactionInterceptor` 在代理里开启/提交事务 |
| MyBatis | 代理 | `MapperProxy` 实现 Mapper 接口，把方法调用翻译成 SQL |
| Feign | 代理 | 接口 + 注解生成 HTTP 客户端 |
| Dubbo | 代理 | 服务引用生成远程调用代理 |

## 六、面试连环问

**Q：Spring 中哪些地方用了工厂模式？**

`BeanFactory` / `ApplicationContext` 根据 BeanDefinition 创建 Bean；`FactoryBean` 让 Bean 自己控制实例化逻辑；`@Bean` 方法本身就是工厂方法；`BeanFactoryPostProcessor` 在实例化前修改定义。

**Q：Spring 中哪些地方用了代理模式？**

AOP（`@Transactional`、`@Cacheable`、`@Async`）、MyBatis Mapper、Feign 客户端、Dubbo 服务引用、Spring 的 `@Lazy` 懒加载代理。

**Q：JDK 代理和 CGLIB 怎么选？**

有接口且不需要代理类本身的方法时用 JDK；无接口或需要代理类（不是接口）时用 CGLIB。Spring Boot 2.x 默认统一 CGLIB，避免“注入实现类失败”的问题。

**Q：静态代理和动态代理的区别？**

静态代理的代理类在编译期就存在，一个接口一个类；动态代理在运行期生成，统一拦截所有方法。动态代理解决了“方法多、代理类爆炸”的问题。

**Q：代理模式和装饰器模式的区别？**

结构几乎一样，区别在意图：代理控制访问（是否调用、何时调用、加权限/事务），装饰器叠加功能（可以嵌套多层，每层加一点）。代理通常自己创建目标对象，装饰器由外部传入。

**Q：为什么 MyBatis 的 Mapper 接口不用写实现类？**

启动时 `MapperScannerConfigurer` 扫描接口，为每个接口注册一个 `MapperFactoryBean`，`getObject()` 返回 JDK 动态代理。调用接口方法时，`MapperProxy` 根据方法名和注解找到对应 SQL 并执行。
