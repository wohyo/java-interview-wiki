# 22. 覆盖索引、索引下推

**一句话定位**：**覆盖索引**解决“要不要回表”，**索引下推**解决“回表之前能不能先过滤”——两者的目标都是减少回表次数。

## 一、覆盖索引

如果一条查询需要的所有列都能从索引里拿到，就不需要回表，`EXPLAIN` 的 `Extra` 会显示 `Using index`。

```sql
CREATE TABLE user (
    id BIGINT PRIMARY KEY,
    name VARCHAR(32),
    age INT,
    address VARCHAR(128),
    KEY idx_name_age (name, age)
);

-- 覆盖索引：name、age 都在 idx_name_age 里，id 是二级索引自带的主键
EXPLAIN SELECT id, name, age FROM user WHERE name = '张三';
-- type=ref, key=idx_name_age, Extra=Using index

-- 不是覆盖索引：address 不在索引里，必须回表
EXPLAIN SELECT id, name, address FROM user WHERE name = '张三';
-- Extra 为空（或 Using where），需要回表
```

`Using index` 和 `Using index condition` 是两回事：

| Extra | 含义 |
| --- | --- |
| `Using index` | 覆盖索引，**完全不用回表** |
| `Using index condition` | 用上了索引下推，但可能仍要回表 |
| `Using where` | 存储引擎返回行后，Server 层还要过滤 |

### 怎么用覆盖索引优化

**场景一：分页深翻页**

```sql
-- 慢：LIMIT 1000000, 20 要回表 1000020 次（或至少扫描 100 万行）
SELECT * FROM orders ORDER BY create_time DESC LIMIT 1000000, 20;

-- 快：先用覆盖索引拿到主键，再回表 20 次
SELECT o.* FROM orders o
JOIN (SELECT id FROM orders ORDER BY create_time DESC LIMIT 1000000, 20) t
  ON o.id = t.id;
```

**场景二：高频统计查询**

```sql
-- 原本要回表取 status
SELECT COUNT(*) FROM orders WHERE user_id = 42 AND status = 1;

-- 建 (user_id, status) 后，COUNT 直接在索引上完成
```

**覆盖索引的代价**：索引列越多，索引越大、写放大越严重。不要为了覆盖一条 SQL 把整行都塞进索引。

## 二、最左前缀原则

联合索引 `(a, b, c)` 的排序规则是：先按 a 排，a 相同按 b 排，b 相同按 c 排。所以只能从最左列开始连续匹配。

| WHERE 条件 | 用到的索引列 | 说明 |
| --- | --- | --- |
| `a = 1` | a | ✅ |
| `a = 1 AND b = 2` | a, b | ✅ |
| `a = 1 AND b = 2 AND c = 3` | a, b, c | ✅ |
| `a = 1 AND c = 3` | a | c 无法定位，只能过滤 |
| `b = 2` | 无 | 跳过最左列 |
| `a > 1 AND b = 2` | a | 范围之后的列不能用于定位 |
| `a = 1 AND b > 2 AND c = 3` | a, b | c 无法定位 |

顺序可以调整：`WHERE b = 2 AND a = 1` 与 `WHERE a = 1 AND b = 2` 等价——优化器会自动按索引顺序重排等值条件。**但范围条件的位置不能随便换**：

```sql
-- 索引用 a 定位，b 只能过滤
WHERE a > 1 AND b = 2

-- 如果业务允许，改成 b 等值在前，索引设计成 (b, a) 更高效
```

`key_len` 可以验证用了几列：`int` 允许 NULL 占 5 字节、不允许 NULL 占 4 字节；`varchar(32) utf8mb4` 占 `32*4+2` 字节（含 2 字节长度）。

## 三、索引下推（ICP）

MySQL 5.6 引入，全称 Index Condition Pushdown。核心是把**能用索引判断的 WHERE 条件**从 Server 层下推到存储引擎层，在回表之前过滤。

```sql
-- 索引 (name, age)
SELECT * FROM user WHERE name LIKE '张%' AND age = 20;
```

### 没有 ICP

```
存储引擎：沿 idx_name_age 扫描，把每个 name 以 '张' 开头的索引项对应的整行回表读出来
          ↓  （假设有 10000 个姓张的，回表 10000 次）
Server 层：对每一行判断 age = 20，过滤掉不满足的
```

### 有 ICP

```
存储引擎：沿索引扫描，在索引项上直接判断 age = 20
          ↓  （只有满足 age=20 的才回表，假设 50 个）
Server 层：拿到已经过滤过的行
```

效果：回表次数从“满足前缀的行数”降到“满足全部索引条件的行数”。`Extra` 显示 `Using index condition`。

### ICP 的适用条件

| 条件 | 说明 |
| --- | --- |
| 访问类型 | `range`、`ref`、`eq_ref`、`ref_or_null` 等需要回表的场景 |
| 条件列 | 必须是索引中的列（不要求是最左前缀），可以是索引列上的 `LIKE`、`BETWEEN`、`IN` |
| 子查询 | 条件下推只针对本表，不涉及子查询 |
| 覆盖索引 | 如果本来就是覆盖索引（不回表），ICP 没有意义 |

ICP 默认开启，可以 `SET optimizer_switch = 'index_condition_pushdown=off'` 关闭做对比。

### ICP 不能解决什么

ICP 只是在**索引层过滤**，它不能改变“最左前缀”的定位能力。`WHERE b = 2`（b 不是最左列）依然无法用 `(a,b)` 索引定位，ICP 也救不了——因为扫描起点就找不到。

## 四、索引跳跃扫描（Skip Scan）

MySQL 8.0.13 引入，针对“联合索引最左列没出现在 WHERE 里、但最左列基数很低”的场景：

```sql
-- 索引 (gender, age)，gender 只有 M/F 两个值
SELECT * FROM user WHERE age = 20;
```

优化器可以把查询拆成 `gender='M' AND age=20` 和 `gender='F' AND age=20` 两次范围扫描，相当于“跳过”最左列。

适用条件：最左列**不同值很少**（基数低），且查询列都在索引中。基数高时拆分的次数太多，优化器不会选。它不是最左前缀的替代品，不要依赖它。

## 五、索引合并（Index Merge）

当 WHERE 是 `OR` 或多个独立条件时，MySQL 可能同时用多个索引再合并结果：

```sql
SELECT * FROM user WHERE name = '张三' OR age = 20;
-- 分别走 idx_name 和 idx_age，再取并集
-- Extra: Using union(idx_name, idx_age)
```

三种形式：`Using intersect(...)`（交集）、`Using union(...)`（并集）、`Using sort_union(...)`（排序后并集）。索引合并通常不如一个设计良好的联合索引，出现它往往说明索引设计可以优化。

## 六、面试连环问

**Q：什么是覆盖索引？**

查询需要的列全部包含在索引里，不需要回表取整行。`EXPLAIN` 的 `Extra` 显示 `Using index`。注意 `SELECT *` 几乎不可能是覆盖索引。

**Q：覆盖索引一定比回表快吗？**

大多数情况是。但如果索引很宽（列多、字符串长），扫描索引的代价可能超过回表，优化器会自己算成本。覆盖索引的价值在于**减少随机 IO**，不是无条件加速。

**Q：最左前缀原则的原理？**

联合索引按定义的列顺序排序，只有从最左列开始才能利用有序性定位。跳过最左列，后面的列在索引中不是全局有序的。

**Q：范围查询后面的列为什么用不上索引？**

`a > 1` 匹配的是多个不连续的 a 值，在每个 a 内部 b 有序，但整体 b 无序，无法二分定位。范围列之后的列只能用于过滤（可能借助 ICP）。

**Q：ICP 和覆盖索引的区别？**

覆盖索引是“不回表”；ICP 是“回表前先在索引层过滤，减少回表次数”。ICP 仍然可能回表，只是回得更少。两者可以同时存在。

**Q：ICP 在什么情况下不生效？**

覆盖索引（本来就不回表）、条件列不在索引中、访问类型是 `ALL`（全表扫描）、或者优化器判断下推不划算时。

**Q：`Using index` 和 `Using index condition` 同时出现说明什么？**

说明查询既用上了覆盖索引，又用上了索引下推。常见于 `SELECT id, name, age FROM user WHERE name LIKE '张%' AND age = 20` 且索引是 `(name, age)` 的场景——索引覆盖了所有列，age 条件也被下推。
