# 7. ConcurrentHashMap

**一句话定位**：JDK 8 的 ConcurrentHashMap 用 **CAS 插入空桶 + synchronized 锁住桶头 + volatile 读** 实现细粒度并发，读操作完全无锁。

## 一、两个版本的结构对比

| 维度 | JDK 1.7 | JDK 1.8 |
| --- | --- | --- |
| 结构 | `Segment[]` + `HashEntry[]` | `Node[]` + 链表 + 红黑树 |
| 锁 | Segment 继承 `ReentrantLock` | `synchronized` 锁单个桶头 |
| 并发度 | 固定 16（Segment 个数） | 等于桶的数量，粒度更细 |
| 空桶插入 | 锁 Segment | CAS，无锁 |
| 扩容 | 每个 Segment 独立扩容 | 多线程协同扩容（helpTransfer） |
| 计数 | `AtomicInteger` 累加 | `baseCount` + `CounterCell[]` |
| 树化 | 无 | 链表 ≥8 且数组 ≥64 转红黑树 |

1.7 的结构长这样：

```java
static final class Segment<K,V> extends ReentrantLock implements Serializable {
    transient volatile HashEntry<K,V>[] table;
    transient int count;
}
```

一个 Segment 就是一把锁，锁住里面的一整张 `HashEntry[]`。并发度在构造时固定，写操作要锁 Segment，读操作靠 `volatile` 保证可见性。

1.8 直接把 Segment 砍掉，锁的粒度降到**单个桶**：

```java
final V putVal(K key, V value, boolean onlyIfAbsent) {
    if (key == null || value == null) throw new NullPointerException();
    int hash = spread(key.hashCode());
    int binCount = 0;
    for (Node<K,V>[] tab = table;;) {
        Node<K,V> f; int n, i, fh;
        if (tab == null || (n = tab.length) == 0)
            tab = initTable();                                   // ① 懒初始化，CAS 抢 sizeCtl
        else if ((f = tabAt(tab, i = (n - 1) & hash)) == null) {
            if (casTabAt(tab, i, null, new Node<K,V>(hash, key, value, null)))
                break;                                           // ② 空桶 CAS 插入，无锁
        }
        else if ((fh = f.hash) == MOVED)
            tab = helpTransfer(tab, f);                          // ③ 正在扩容，帮忙搬
        else {
            V oldVal = null;
            synchronized (f) {                                   // ④ 锁住桶头
                if (tabAt(tab, i) == f) {
                    if (fh >= 0) {
                        binCount = 1;
                        for (Node<K,V> e = f;; ++binCount) {
                            K ek;
                            if (e.hash == hash && ((ek = e.key) == key || (ek != null && key.equals(ek)))) {
                                oldVal = e.val;
                                if (!onlyIfAbsent) e.val = value;
                                break;
                            }
                            Node<K,V> pred = e;
                            if ((e = e.next) == null) {
                                pred.next = new Node<K,V>(hash, key, value, null);
                                break;                           // 尾插
                            }
                        }
                    }
                    else if (f instanceof TreeBin) { /* 红黑树插入 */ }
                }
            }
            if (binCount != 0) {
                if (binCount >= TREEIFY_THRESHOLD)
                    treeifyBin(tab, i);                              // ⑤ 树化
                if (oldVal != null) return oldVal;
                break;
            }
        }
    }
    addCount(1L, binCount);                                      // ⑥ 计数
    return null;
}
```

## 二、读操作为什么完全无锁

```java
public V get(Object key) {
    Node<K,V>[] tab; Node<K,V> e, p; int n, eh; K ek;
    int h = spread(key.hashCode());
    if ((tab = table) != null && (n = tab.length) > 0 &&
        (e = tabAt(tab, (n - 1) & h)) != null) {
        if ((eh = e.hash) == h) {
            if ((ek = e.key) == key || (ek != null && key.equals(ek)))
                return e.val;
        }
        else if (eh < 0)
            return (p = e.find(h, key)) != null ? p.val : null;   // 树节点或 ForwardingNode
        while ((e = e.next) != null) {
            if (e.hash == h && ((ek = e.key) == key || (ek != null && key.equals(ek))))
                return e.val;
        }
    }
    return null;
}
```

无锁的前提是三个 `volatile`：

| 字段 | 作用 |
| --- | --- |
| `table`（`volatile Node[]`） | 扩容后新数组对所有线程可见 |
| `next`（`volatile Node next`） | 尾插的节点对读线程可见 |
| `val`（`volatile V val`） | 值修改对读线程可见 |

`Node.val` 和 `Node.next` 在 JDK 8 里都是 `volatile` 的，所以读线程要么看到完整旧链、要么看到完整新链，不会读到“半截指针”。这也是读操作能完全无锁的原因。

## 三、扩容：多线程协同搬运

1.8 的扩容不是“锁住整张表”，而是**分桶迁移**：

1. 每个线程领一段桶区间（stride 至少 16），从后往前搬。
2. 搬完一个桶，就把旧数组该位置设为 `ForwardingNode`（`hash = MOVED = -1`）。
3. 其他线程 put 时遇到 `MOVED`，调用 `helpTransfer` 加入搬运，而不是阻塞等待。
4. 搬运完成后，`table` 指向新数组，`sizeCtl` 更新为新阈值。

::: tip
`ForwardingNode.find()` 会转发到新数组查找，所以**扩容期间读操作依然可用**，这是 1.8 相比 1.7 最大的体验提升——1.7 扩容时读可能被阻塞在 Segment 上。

:::

## 四、计数：为什么不用 AtomicLong

高并发下所有线程 CAS 同一个 `AtomicLong`，会形成热点，CPU 空转严重。1.8 采用类似 `LongAdder` 的思路：

```java
private transient volatile long baseCount;             // 基础计数
private transient volatile CounterCell[] counterCells; // 分散计数槽

// 伪代码
if (cas 成功更新 baseCount) return;
else 根据当前线程的 probe 值，CAS 更新某个 CounterCell；
    失败则扩容 counterCells 数组，继续分散。
// size() = baseCount + 所有 CounterCell 之和
```

| 方案 | 原理 | 高并发表现 |
| --- | --- | --- |
| `AtomicLong` | 所有线程 CAS 一个变量 | 竞争激烈，失败重试多 |
| `baseCount` + `CounterCell` | 按线程散列到不同槽，各自累加 | 冲突少，近似线性扩展 |

代价是 `size()` 需要遍历求和，返回的是**近似值**（求和过程中可能有并发修改），不强一致是设计上的取舍。

## 五、为什么用 synchronized 而不是 ReentrantLock

| 理由 | 说明 |
| --- | --- |
| 锁粒度极细 | 只锁一个桶头的插入/树化，临界区只有几十行，用不到超时、可中断、公平锁这些高级功能 |
| 空间更省 | `synchronized` 用对象头 Mark Word，不额外创建锁对象；每个桶都挂一个 `ReentrantLock` 会多出大量对象 |
| 代码更短 | 不需要 try-finally 释放，异常时由 JVM 保证释放 |
| JIT 优化充分 | 1.6 之后锁消除、锁粗化、自适应自旋、偏向锁（JDK 15 前）都作用于 `synchronized` |

一句话：**临界区短、功能需求简单，重量级 API 反而是负担**。

## 六、为什么不允许 null

```java
if (key == null || value == null) throw new NullPointerException();
```

`get(key)` 返回 null 时，无法区分“这个 key 不存在”和“这个 key 存在但值是 null”。单线程的 HashMap 允许 null，是因为调用方可以用 `containsKey` 兜底；但在并发场景下，`containsKey` 和 `get` 之间状态可能变化，这个兜底并不可靠，所以干脆禁止。

## 七、常见追问

**Q：ConcurrentHashMap 的 size() 是精确的吗？**

不是。它由 `baseCount` 和各 `CounterCell` 求和得到，求和期间其他线程可能仍在写入，所以是近似值。需要精确值时只能加锁（不推荐）。

**Q：1.8 的并发度是多少？**

不再是固定的 16。理论上等于桶的数量（默认 16，扩容后增大），同一时刻不同桶可以并行写。实际并发度还受 CPU 核数、冲突分布影响。

**Q：ConcurrentHashMap 的 key 能为 null 吗？**

不能，key 和 value 都不能为 null，直接抛 NPE。

**Q：为什么 1.8 的 get 不需要加锁？**

因为 `table`、`next`、`val` 都是 volatile，读线程不会看到半成品；扩容时通过 `ForwardingNode` 转发，读也不会被阻塞。

**Q：ConcurrentHashMap 能保证复合操作原子吗？**

不能。`if (!map.containsKey(k)) map.put(k, v)` 仍然有竞态，要用 `putIfAbsent`、`computeIfAbsent`、`merge` 这些原子方法。

**Q：ConcurrentHashMap 的迭代器是强一致的吗？**

不是。它是**弱一致**（weakly consistent）迭代器：不抛 `ConcurrentModificationException`，能遍历到创建后新增的元素，但可能看不到遍历过程中的全部修改。这是为了无锁读做的取舍。
